## B. 跨机通道：**不通**
cap/crates/linkd/src/lib.rs:7
  「v0 不做网络传输/relay/vsock；先落 UDS 上的数据面语义。」
  ⇒ link.peer.register / link.mail.* / link.file.* 只是**同机 UDS** 上的语义，
    不是跨机 poke。设备互联的"传输腿"没有落码。
docs/design/05-distribution.md:196-212
  「L4 只能被控机本地执行（分布性由层推出）」——核侧只产生"已判定的命令"，
  跨机腿只做下发，落地执行在设备本机；跨机不换层位、不产生跨机主体。
  同件 §三「跨机一跳＝独立网络腿（核侧发起·同步请求-响应最小形·无服务器推送）」，
  通道形态=ⓑ；改判⟶ⓐ（长连）的触发条件=需设备侧主动推送。

## C. relay 隧道：**能跨机，但形态是"反向 Web 隧道"，不是作业通道**

    浏览器访问 https://<route>.<domain>/，与本地访问同功能。」
docs/design/relay-tunnel.md:21-24  relay 维护 route→隧道 内存表；不解析业务帧，只转发字节。
docs/design/relay-tunnel.md:132  「每设备并发流上限 64」；:137「每设备并发流上限 64；隧道空闲 60s 回收」

  在 P5 前不得对外称零知识或端到端加密。」

## D. 应用面协议（唯一可跨机复用的"下发原语"）
docs/design/triple-app-standard.md §5：
  POST /app/v1/command  {id, op, args} → {id, ok, result}
  · id 由客户端生成，服务端按 id 幂等（同 id 重放返回首次结果）
  · 未知 op 必须拒绝（fail-closed）
  事件流：GET /app/v1/events（SSE/NDJSON，topic+seq+回放）
实测 op 面（cap/apps/stand/src/main.rs, feat/stand-parity-flow）：
  :5040  ("POST","/app/v1/command") => app_v1_command(...)
  :8783  "session.create"   :8799 "session.list"   :8802 "session.history"
  :8811  "turn.submit"      :8926-8929 turn.started / turn.done / turn.error / session.opened
  :147   DELEGATE_CONTROL_CAPABILITIES = ["delegate.create","delegate.health"]
  ⇒ 这就是"下发一轮任务 + 流式取事件 + 终态"的原语，且是**标准 HTTP+SSE**，
    不绑定传输，理论上可指向任意可达主机的 18080。

## F. 资源与隔离（有机制）
docs/design/oci-superset.md:56-63
  两档：轻档＝宿主进程 + cgroup 域（宿主内核 BPF，cgroup id 键）；
        强隔离档＝每单元一 KVM microVM（Firecracker 首选）。
  轻档诚实边界：「无 seccomp/userns/cap 收窄/overlay——非安全边界」。
  轻档实测启动 3.6ms（裸进程 0.8ms）。
docs/design/oci-superset.md:78-82 执法映射：
  ①只读 rootfs ②只挂本单元 vol ③默认无网卡 ④VMM 进程入宿主 cgroup（cpu/mem/pids 限额）
  ⑤不暴露宿主目录（无 virtiofs/9p）⑥镜像 digest 钉住。
docs/design/oci-superset.md:103-108 已落批次：
  批88「每设备 cgroup 限额 cpu.weight/memory.max/pids.max 回读」
  批89「cpu.max/租约/GC：cpu_quota/cpu_period；slot 磁盘租约；DEVICE-GC」

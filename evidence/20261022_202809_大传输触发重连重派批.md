## ② 服务端根因（代码机制，双证钉死）

`NeblinkRelayTunnel.scala:1769`（修前）：

```scala
case "ping" =>
  try ws.sendText("""{"type":"pong"}""", true)
  catch case _: Exception => ()
```

- **本 JDK 不同步抛**：Temurin 23 `WebSocketImpl.sendText` 在单发位被 bulk 帧占住时返回**已失败 future**（`IllegalStateException("Send pending")`）——同仓 `NeblinkRelayTunnelHeartbeatSendSpec` P1 **真 RFC 6455 socket 夹具**已契约钉死（16MiB 洪泛 + 对端不读 ⇒ 确定性饱和）。
- 修前代码**无视返回 future** ⇒ bulk 洪峰期 pong **静默丢失**（try/catch 抓不到， future 无人看）。
- **relay 侧判死口径 = 2-miss liveness**（本仓 `PortalTunnelBridge` mailbox 注释原文：「backpressure here would stall ping/pong and get a live tunnel killed by the **2-miss liveness check**」）⇒ 连丢 2 拍 pong ⇒ relay 撕隧道。
- 撕的瞬间在飞 portal 周期全部报 `portal http cycle failed: Output closed`（= ①类 1 的伴生指纹），隧道 0.5s 重连，但**骑隧道的浏览器 WS 已死 ⇒ 全体重连**。

**完整因果链**：大传输（本机文件经隧道读 / 跨设备 nf-file 流）⇒ bulk 帧连续占住 JDK 单发位 ⇒ relay ping 的 pong 裸发送被拒、future 被无视 ⇒ relay 连 2 拍无 pong ⇒ relay 判死撕隧道 ⇒ 浏览器 WS 重连风暴 = 作者「每次大传输就触发重连」。白天每次隧道撕（①表）都是这条链的实拍。

同族-but-不修（请求级丢失，各有兜底）：relay_response（每请求超时）、mail-ack（at-least-once 重放，DeviceMailAckHonestySpec）、bind_confirm。唯有 **pong 丢失喂的是连接级活性计数**，故只修这一口。

## ③ 修法（服务端腿，pong-reliability）

- `PortalTunnelBridge.scala`：+`PortalTunnelBridge.controlSender`（包内授权访问器）；+`PortalConnection.sendControlText(text, ws)`——桥已绑 ⇒ pong 过 **RelayFrameSender**（与业务 bulk 同一把单发位锁：Send pending 重试 + 15s 预算；持锁等在飞帧写完即上，bulk 泵取不到位 ⇒ **pong 不会被洪峰饿死**；失败显化 debug 留痕，永不撕连接）；桥未绑（upgrade 竞态窗，此窗内不可能有 bulk）⇒ 回落修前裸发语义。
- `NeblinkRelayTunnel.scala`：`case "ping"` ⇒ `portalConn.sendControlText(pong, ws)`。

**与任务书候选修法对应**：「心跳发送与业务 IO 隔离」经既有 RelayFrameSender 串行点实现（pong 与 bulk 同锁互斥、顺序保持），零新增阈值轴、零专用线程池；「宽容窗」不需要——pong 从「丢」变「必达/响亮失败」，relay 计数器不再被饿。

# 定位器纪律（locator discipline）——必读

定位器纪律是这套方法里**最值钱**的一块：它把「靠运气点中」变成「靠事实点中」。

## 一、观测是定位的唯一真源

- 手上有最近一次的相关观测 ⇒ **留着复用**，直到导航或 UI 变化让它过期。
- 定位器**只能**从那次观测里**实际出现**的 role / 可访问名 / 文案 / 属性（`data-*`、`href`、`placeholder`）
  构造。
- **绝不猜** label、可访问名、placeholder、选择器、URL 形态、元素类型。
  猜出来的定位器**不是探针**。
- 会转的搜索建议**不是稳定的 placeholder 契约**。观测里只有一个无名输入框 ⇒
  用 `getByRole('textbox')` 配 `count()`，不要凭空编一个 `getByPlaceholder('Search')`。
- 观测已包含目标 ⇒ **直接用**。不要写 `evaluate` 去重新发现元素、枚举输入框、dump HTML、
  遍历 DOM，或去探测一个猜出来的选择器。
- 不要 dump 整页 `body` 文本、也不要拿一个宽泛定位器循环去「发现」页面：一次有界观测，然后收窄。

## 二、可点击性与 role 的常见误判

- 观测里证明存在的**标题或可见文案**，不需要 `link` / `button` role 就能点。
  **不要**把观测里的 `heading` 换成猜出来的 `link` role。
- 用户已授权导航、且该标题/文案目标**唯一**时 ⇒ 直接点它；
  DOM 点击事件可能冒泡到祖先卡片上的脚本处理器 —— 那是正常现象。
- 源码顺序 ≠ 视觉顺序：定位一律按**可见状态**。

## 三、配方：动作前必走的四步

对 click / fill / press / select / check 等**会改状态**的定位器动作：

1. 复用最近一次相关观测；过期或不完整 ⇒ 重取一次。
2. 用那些事实构造**最稳**的定位器。
3. 唯一性不是显然的 ⇒ 调一次 `count()` 并留下结果。
4. 只有解析到**恰好一个**预期元素才继续。

然后：动作做**一次**，再取下一个决策所需的最小观测。**一个观测周期里只做一个状态变更动作。**

- `count() === 0` ⇒ **不要**执行动作、**不要**等这个定位器；重取观测后重建。
- `count() > 1` ⇒ 收紧到稳定容器或更强属性；**不要**用 `first()` / `last()` / `nth()` 掩盖歧义。

## 四、稳定度优先序

1. 稳定的 test id 或 `data-*` 属性；
2. 稳定的精确 `href` 或同类持久属性；
3. 限定作用域的语义 role + 观测到的可访问名；
4. 限定作用域的可见文案；
5. 从已知 DOM 事实复制的限定选择器；
6. 作用域内的坐标路径（观测读不到时）。

`Search` / `Menu` / `Close` 这类通用名、以及重复出现的标题，**默认歧义**：动作前先限定作用域。

## 五、超时与恢复

- 常规定位、等待、只读求值都用**短失败预算**；超时是「重建定位器」的信号，**不是**「原样重试」的信号。
- 导航后、读标题/URL/内容**之前**，显式确认一次加载状态。
- 不要用 `networkidle` 做常规等待 —— 等 `load` / `domcontentloaded` 或一个**具体**的页面状态。
- **原页面 URL 没变 ≠ 点击失败**。按「期望效果是否出现」判。
- 期望效果可能在别处出现（新页/新状态）⇒ **同一轮**无条件读取所有相关来源，再决策。

## 六、超时/严格模式/选择器解析失败之后

1. **不要**重试同一个定位器；
2. 重新观测一次；
3. 确认目标是否还存在；
4. 从更紧的作用域或更稳的属性重建。

同一目标**两次**失败 ⇒ 停止加大 role/文案复杂度，果断换到最强稳定属性或限定作用域的坐标路径。

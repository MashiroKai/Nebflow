# explorer-toolkit — 插件使用指导（Plugin.md）

> 本文件是 explorer-toolkit 插件的**包根使用指导件**（Plugin.md）：**插件分配时注入给 agent 的提示词 = 本文件内容**（作者令 2026-10-21「plugin.md = 插件必要文件机制」批；SKILL.md 回归按需查阅件——面板胶囊点击打开，不再随分配整文注入）。选配判定仍看 plugin.json 的 description；逐 skill 作业指令见各 `skills/<skill>/SKILL.md`（按需查阅）。**本文件是导览不是手册：与 SKILL.md 不一致时以 SKILL.md 为准并回改本文。** 文内路径均为**自包根的文件相对形式**（不使用 `${SKILL_DIR}`）。

## 1. 速览

explorer-toolkit 是代码库探索与方案规划方法包：节点获得一条「先摸清现状、再定怎么做」的完整链路——每条论断可按图索骥复核的探索纪律，与动手前先定验收标准的方案设计纪律。内含 2 个 skill：

- `skills/exploration-method/`——探索与举证方法论：先入口后发散的探索路径、Glob/Grep/Read 三件套工具纪律、「路径+行号」举证纪律、结论先行的汇报结构、单次调用会话纪律。
- `skills/solution-planning/`——方案与验收条件设计方法论：方案前置澄清纪律、方案结构五件套（现状/方向/涉及文件/预期变更展示/验收条件）、分档验收条件方法论（冒烟红线/端到端/后端/前端三层/自查清单）、活文档落盘规范、反模式清单。

**包纪律一句话**：探索的目标不是「看过代码」，而是每条论断都可被第三方复核；方案的硬通货是验收条件——动手之前先定义「怎么算做完、怎么算做对」。需求拆解与 trade-off 调研不在本包（另配 `engineering-methods` 插件）。

## 2. 安装与启用

- **安装**：本包属 Nebflow seed 官方分发，随实例 seed mirror 自动下发，无需手工安装。
- **启用/选配**：装载为「在位即生效」；分发器按 description 触发词选配（探索陌生代码库、读代码定位入口、盘点代码结构、写技术方案、设计验收条件、规划实施步骤等），派发时两份 SKILL.md 全文注入节点。
- **停用**：面板「更多 → 封禁该插件」/ `POST /api/plugins/explorer-toolkit/revoke` / `nebflow plugin revoke explorer-toolkit`。
- **内容变更**：包内任何字节改动都会漂移 digest，面板把该包标为「内容已变更」（可见性提示，不拦截装载；新内容对新派发即刻生效）。

## 4. 包级核心用法（探索→规划链路怎么走）

> 全量口径以注入的两份 SKILL.md 为准；本节是链路速查。

| 步 | 做什么 | 关键判据 | 全量口径 |
|---|---|---|---|
| ① 探索 | 先入口后发散：定位入口面（README/主函数/路由注册表/registry/构建文件）→ 顺调用链下钻 → 主干清楚后再向边缘发散 | 不从随机文件泛读起手；三件套分工——Glob 答「在哪」、Grep 答「哪里有」、Read 答「是什么」；禁 find/ls/bash grep | exploration-method §1-2 |
| ② 举证 | 每条代码事实论断附 `路径:行号` 锚点 | 格式＝项目内相对路径:起止行；给不出行号＝未验证的猜测，要么查实要么显式标注，禁把猜测写成事实 | exploration-method §3 |
| ③ 汇报 | 结论先行的固定骨架：结论（一段话）→ 关键证据（锚点表）→ 细节与结构 → 未决项 | 禁按时间顺序记流水账、禁把结论埋在细节后 | exploration-method §4 |
| ④ 澄清 | 方案动笔前的前置澄清 | 必须问：多方向影响架构/体验、缺关键信息；不问：有合理默认——写明假设直接推进；用可点击选项一次问完 | solution-planning §1 |
| ⑤ 规划 | 方案五件套，顺序不变 | 现状每条带锚点（沿用②）；方向写取舍不只写结论；涉及文件标改动性质；预期变更展示让人不动手也能看见结果 | solution-planning §2 |
| ⑥ 验收 | 验收条件二值可判定＋每条有验证手段，按改动类型分档 | 冒烟红线最先跑、失败即停；端到端走真实路径；后端查契约/错误路径/持久化重读；前端三层递进（资源层/DOM 层/交互层截图）缺一不可；自查逐条 PASS/FAIL＋证据 | solution-planning §3 |
| ⑦ 落盘 | 活文档规范 | 头部带状态字段；事实偏差回写原档，不另起矛盾新版本；方案确认后再动工，文档与实现保持同步 | solution-planning §4 |

- **单链路纪律**：探索与后续规划通常在**单次调用**内完成，不拆成多轮等指令；探索产出的锚点直接进方案的「现状」节——两 skill 是上下游关系，不是二选一。
- **与其他包的分工**：需求拆解与 trade-off 调研另配 `engineering-methods`；方案出图另配 `visual-report`；执行验证另配 `nebflow-qa`。

## 6. 选 skill 决策树

- 「先摸清现状」类任务（定位功能实现、理解调用链、盘点结构、查证外部资料）→ `exploration-method`。
- 已摸清现状、要把「要做什么」落成结构化方案（动手前定验收标准）→ `solution-planning`。
- 两者常连用：一次探索任务＝exploration-method 出可复核结论 ＋ solution-planning 出可验收方案，单次调用内完成。
- 需求拆解、技术选型、多视角调研 → 不进本包：另配 `engineering-methods`。
- 方案需要出图（架构图/流程图/图表）→ 另配 `visual-report`。
- 执行验证与交付把关 → 不进本包：另配 `nebflow-qa`。

## 9. 维护约定

- **上下游口径同步**：exploration-method 的锚点格式与 solution-planning「现状」节的举证要求是同一条纪律的两端——改其一须核另一侧表述未被架空。
- **反模式清单**：随生产踩坑更新 solution-planning §5；更新时核对分档验收各节未被推翻。
- **本文件定位**：Plugin.md 是按需 Read 面——装载器不注入；SKILL.md 是注入面权威，两者不一致时以 SKILL.md 为准并回改本文。

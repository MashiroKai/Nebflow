# Design Spec — 设计规格书与视觉评审方法论

职责 = 上游「设计先行」产出设计规格书 + 下游「视觉评审」对照规格书验收。**只设计不写产品代码**：写权限仅用于规格书 / 评审报告 / 案例库条目，禁止修改任何产品源码。

## 1. 角色边界（谁做什么）

| 环节 | 设计方（本 skill 使用者） | 其他人 |
|---|---|---|
| 设计规格书（检索 + 产出） | 负责 | — |
| 实现 | 不碰 | 实现方（前端/客户端开发者） |
| 功能验收（冒烟/契约/资源/DOM 断言） | 不做 | QA |
| 规格书 §8 可断言点 → 自动化断言 | 定义可断言点 | QA 转 Playwright 进 CI |
| 视觉评审（截图 + vision 对照规格书） | 负责 | QA 不重复做 |
| 教训沉淀 | 归因入案例库 | 实现方/QA 汇报所见问题 |

**与 QA 交叉验证（防误报）**：视觉评审结论必须与二进制取证交叉验证——引用 QA 的 Playwright DOM 断言结果与截图路径作佐证，**绝不裸看图下 PASS/FAIL**（vision 对「是否已修复」的精细判断会误报）。

## 2. 四道防线工作流

### 防线 1 · 设计先行（上游，出规格书）
1. 必读项目视觉铁律 skill（如 Nebflow 的 `visual-style`，nebflow-frontend-dev 插件，用户裁定硬规则，最高优先级）；若已有设计案例库 skill（如 `design-system`，nebflow-frontend-dev 插件）则同时必读；
2. 检索：按功能类型命中 1-2 个权威范式（检索源清单见 §4），用 WebSearch/WebFetch 拿原文 → 提炼 3-8 条可执行规则；
3. 产出规格书：按 §3 模板写入 `docs/<域>/<feature>-spec.md` 活文档（头部状态字段 draft→frozen→dispatch→shipped；禁用 /tmp 路径）；
4. 确认：展示规格书；歧义处用 AskUserQuestion 问用户；用户/管理者确认后**冻结**。

### 防线 2 · 规格化实现（中游）
规格书是实现的唯一依据；规格书未定义之处 → 指示实现方回问，不自由发挥。

### 防线 3 · 双重验收（下游，视觉评审）
隔离实例截图（亮/暗主题、响应式断点如 768/375、关键状态）→ vision 对照规格书逐项核对 → 输出 PASS/FAIL 报告（附截图证据 + DOM 断言交叉验证）。PASS 交管理者合入；FAIL 打回实现方附证据清单。

### 防线 4 · 教训沉淀（反馈环，[DESIGN-LESSON]）
已交付 UI 被打回时归因四类，记录进设计案例库（如 `design-system`），下次设计必读：
1. **裁定冲突** → 升级用户裁定请求 → 视觉铁律 skill 替换式更新；
2. **缺参考** → 设计时没检索到范式 → 检索协议补条 + 案例库新增；
3. **规格缺失** → 状态/边界/动效没写进规格书 → 规格书模板补项；
4. **实现走样** → 按规格做但做错 → 评审 checklist 补项。

## 3. 设计规格书模板（§0-9，每次按此结构产出）

- **§0 一句话目标**
- **§1 参考与依据**：平台规范 / 行业范式 / 既有裁定，**每个引用带链接**
- **§2 布局与信息架构**：引用既有 design token，禁新 token（除非显式新增并说明理由）
- **§3 交互状态机表**：默认 / hover / focus / active / disabled / loading / error / empty
- **§4 动效规范**：触发 / 时长 ms / 缓动 / 位移 / 是否尊重 prefers-reduced-motion
- **§5 视觉规格**：字体 / 字重 / 颜色 / 圆角 / 边框 / 阴影 / 玻璃质感，**全部 token 引用**
- **§6 边界与异常**：空态 / 错误态 / 超长文本 / 窄视口 / 多语言
- **§7 无障碍**：键盘导航 / focus ring / ARIA / 对比度 ≥4.5:1 / 非鼠标可达
- **§8 可断言验收点**：**≥5 条，二值判断 + 是否需截图**，供 QA 转 Playwright 断言。凡涉及文案（→i18n key）、顺序/选中（→显式状态语义）、布局度量（→增量基线口径）的断言，写规格书时就锁死口径，否则验收阶段必然返工
- **§9 参考链接**

## 4. 检索源清单

- **平台 HIG**：Apple HIG（developer.apple.com/design/human-interface-guidelines）· Google Material 3（m3.material.io）· Microsoft Fluent 2（fluent2.microsoft.design）
- **成熟产品范式**：微信 / Telegram / Discord（消息搜索/聊天/侧栏）· Apple 系统应用（设置/Spotlight）· Linear / Notion / Slack（命令面板/空态/批量操作）· VS Code（面板布局/设置）
- **组件库模式**：antd · Radix UI / shadcn/ui · WAI-ARIA APG（w3.org/WAI/ARIA/apg）
- **动效**：Material Motion · cubic-bezier.com
- **项目内部**：视觉铁律 skill（最高优先级）· 设计案例库 skill · 既有样式表与组件清单（design token 来源）

**冲突取舍**：范式之间冲突时以项目视觉铁律与用户 taste（如「低调克制专业感」）为准，规格书写明取舍理由。

## 5. 硬约束

- **只设计不写产品代码**：写权限仅用于规格书/评审报告/案例库条目，禁改任何团队源码；
- 规格书引用全部带链接，可追溯；
- 视觉评审必须截图证据 + DOM 断言交叉验证，**绝不裸看图下结论**；
- 不碰运行中的活实例；隔离实例按对应团队惯例启动；
- 产出展示给管理者/用户；**结论二值化（PASS/FAIL + 证据清单）**。

## 6. 配合关系（跨插件按名引用）

本 plugin 不含视觉规则与案例库本体——以下能力已随 2026-09-05 skills→plugins 迁移进入插件（原 user 层 skill 形态不复存在），本 skill 按名引用、注入后由 agent 自行 Read 配合（`${SKILL_DIR}` 不跨包，正文中不写跨包相对路径）：

- **`visual-style`**（nebflow-frontend-dev 插件）：用户视觉裁定硬规则，最高优先级——防线 1 第 1 步必读；与本 skill 检索到的外部范式冲突时以它为准；
- **`design-system`**（nebflow-frontend-dev 插件）：防线 4 教训沉淀的载体 + 防线 1 检索时的内部先例来源；
- **`card-design`**（design-cards 插件）：评审/汇报产出 HTML 卡片时的视觉规范。

**mcp.json 说明**：本 plugin 无外部服务依赖，按协议（skills 与 mcp.json 至少有其一即可）省略 mcp.json——这是合法形态，非缺漏。

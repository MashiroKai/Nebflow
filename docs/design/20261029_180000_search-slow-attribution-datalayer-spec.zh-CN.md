# 聊天记录检索归因 + 数据层检索骨架方案（分片索引 · 增量维护 · 结果缓存）

> 作者报障 2026-10-29 17:06 逐字：「我们目前的这个聊天记录检索速度非常慢，归因为什么，然后给我提一下这个解决方案」。
> 作者扩充 2026-10-29 17:17 四条：①分片+增量 ②多选一次打开 ③跨设备缓存（结果凭证层）④固化为**数据层通用方案**（不只服务聊天检索一个场景）。
> 本档只做归因 + 提案，**零实施代码**（作者批方案后再派实施批）。所有实测数字都在本机真实数据上取得（测量方法与复现命令见 §6），数据规模：会话历史 6,513 个 `.ui.json` 共 944 MB、共 20.5 万条可检索行 / 7.0 亿字符。

## 0. 结论先行（一段话）

慢的根源**不在渲染、不在单会话**：当前会话档全链路 ≈90 ms（可用）；**「全部会话」档把整库扫了一遍**——前端先拉全量会话清单（磁盘扫 6,509 个文件 ≈0.2-0.4 s），再按 4 并发把 **7,007 个会话的完整历史全部拉回浏览器**（约 0.9 GB JSON，本机实测 210-237 s 才拉完），逐条反序列化+关键词匹配后才出结果。这是**无索引的全量扫**：每次搜索、每次开面板、甚至慢打字的每一个字符都重复整库搬运。解决方案按作者四条扩充升级为**数据层通用检索骨架**：SQLite FTS5 分片索引（按类型×时间切分片）+ 写路径钩子增量维护（复用既有 debounced flush）+ 查询凭证层跨设备复用（复用既有 `HttpCache` ETag 语义与 `nfFileCache` 账本语义），聊天检索只是第一个接入场景。原型已在**同一份真实数据**上验证：冷建库 41-56 s（一次性）、查询 1.5-10 ms 出 top50、单会话增量更新 0.5 s——把「全部会话」检索从 **3.5 分钟量级压到 0.1 秒量级（~2000×）**。

## 1. 检索链路（读码）

链路一句话：面板 `#search-overlay` → `js/chatSearch.js` → REST `/api/sessions*` → `SessionRoutes` → `SessionStore`（磁盘 JSON）。搜索本身**没有后端搜索 API**——匹配发生在浏览器里。

| 步 | 环节 | 权威落点（仓内相对路径:行号） | 行为 |
|---|---|---|---|
| 1 | 打开面板 | `src/main/resources/web/js/chatSearch.js:264`（`openSearchModal`→`triggerSearch`） | 每次打开都是全新状态（`:267` resetSearchState），立即发起首查 |
| 2 | 模式分发 | `chatSearch.js:785`（`triggerSearch`）：关键词非空→`runSearch`（`:1194`），空→`runStream`（`:1017`） | 桌面范围 select：`current`（当前会话）/ `all`（全部会话）；`isGrouped`（`:124`）判档 |
| 3 | 会话清单 | `chatSearch.js:797`（`fetchSessionList`）→ `GET /api/sessions?includeUnindexed=1` → `src/main/scala/nebflow/gateway/SessionRoutes.scala:56` → `SessionStore.listSessionsIncludeUnindexed`（`src/main/scala/nebflow/core/SessionStore.scala:766`） | 后端为补齐未入索引的 delegate/subtask 会话**逐请求 `os.list` 磁盘 + stat 每个文件**（注解自述「~550 files」已漂移到 6,509 个） |
| 4 | 拉历史 | `chatSearch.js:814`（`fetchHistory`）→ `GET /api/sessions/{id}/history` → `SessionRoutes.scala:74` → `SessionStore.getUiMessages(sid, 0, 0)`（`SessionStore.scala:1782`） | **limit≤0 = 不限条数**（`:1787`）⇒ 整份 `.ui.json` 全量返回；URL 里的 `before/after/limit` 光标参数后端一律忽略（前端注释自认，`chatSearch.js:807-809`「today's backend ignores them and returns the full history」；实测 §5.5 证实） |
| 5 | 反序列化+归一 | `chatSearch.js:1237`（逐会话 `fetchHistory` 无 cursor）→ `normalizeAll`（`:995`）+ `indexMedia`（`js/popMediaIndex.js`） | 前端把每份历史 JSON.parse、逐行抽可检索文本、建媒体条目索引 |
| 6 | 匹配 | `chatSearch.js:1272-1298`：`m.text.toLowerCase().includes(kwLower)` 逐行子串匹配 | 纯前端线性扫描；无索引、无分词、无排序（按 ts 排序后截 200 条，`:1301-1302`） |
| 7 | 渲染 | `chatSearch.js:1367`（`buildModel`）→ `renderStreamFresh`（`:1397`）→ `renderNextBatch`（`:1458`，50 条/批 IntersectionObserver 懒渲染） | 渲染已有分批+虚拟化按需加载设计，非瓶颈（§5.6） |

缓存面现状：`/api/*` 全树无 ETag/条件请求（`SessionRoutes.scala:74-79` 裸 `Ok(...)`；`HttpCache.scala` 的条件请求小刀只服务六个别的端点）；`GET /history` 响应无任何缓存头，**同一份数据每查必重发**。网关侧有 UI 历史 LRU 内存缓存（`SessionStore.uiCacheState`，32 条/256MB，`src/main/scala/nebflow/shared/Defaults.scala:747,761`）但那只加速**服务端**读盘，字节照样全量过网。

## 3. 实测归因（「全部会话」档为何慢到不可用）

### 3.1 逐段分解（活体测量，headless Chromium 驱动真面板 + 插桩 fetch）

对「全部会话 + 关键词 delegate」实测三次（两次会话间有新会话写入，数字为量级参考）：

| 段 | 读数 | 占比 |
|---|---|---|
| 会话清单 `?includeUnindexed=1`（含后端磁盘扫描） | 0.2-1.7 s | <1% |
| **7,007 个 `/history` 请求总耗时**（前端 4 并发，网络腿+服务端读盘+反序列化+传输） | **210 / 227 / 237 s** | **>95%** |
| 前端 JSON.parse + 文本抽取 + 匹配 | 数秒（可与网络重叠，非临界路径主导） | ~1-3% |
| 首行落 DOM（搜索结果出现） | 拉完最慢的那个会话之后 | — |
| 结果渲染 | 50 行/459 节点，瞬时 | <1% |

对照基线（同一台机、同一时刻）：

| 场景 | 实测 |
|---|---|
| **当前会话**档搜索（6.8 MB 历史，全链路 fetch→parse→匹配→渲染） | **88-151 ms**（重复查 80-151 ms） |
| 单会话 `/history` 服务端响应（最大会话，热缓存） | 40-70 ms / 6.9 MB |
| 会话清单（索引-only，侧边栏走的那条） | **7 ms**；加 `includeUnindexed=1`（磁盘扫描）→ 200-429 ms |
| 慢打字 "delegate"（每键间隔 >300ms 去抖窗） | **8 次按键 = 8 次整份历史重取 = 53.1 MB 解码字节**；全部会话档同打字节奏放大 7,007 倍 |
| 重复搜索（同一关键词二查） | **零复用**：再拉 7,007 次（227 s→237 s，没有变快） |

### 3.2 候选归因逐一核实（作者要求 §2 的候选清单）

| # | 候选归因 | 核实结果 | 证据 |
|---|---|---|---|
| 1 | 无索引全量扫，每查全读历史文件 | **成立，主因**。匹配 = 前端 `includes()` 线性扫（§1 步6）；「全部会话」档每次搜索把 944 MB/7,007 会话全部拉回浏览器。实测 210-237 s（§3.1）；纯客户端等价复算（同数据本地全读+解析+匹配）37 s，其中读盘 6.7 s / JSON.parse 18.4 s / 匹配 12.0 s——即「零网络下限」也要 37 s | §1 步6；§5.3 |
| 2 | 跨会话全扫（当前会话/全部 Agent 筛选是否都全库扫） | **部分成立**。`current` 档只拉 1 个会话（快，88 ms）；`all` 档全库扫；「全部 Agent」筛选只是**先全库拉完再在前端过滤**（`chatSearch.js:1232`），不减少任何字节。Agent/工具筛选当前是「先付全款再打折」 | `chatSearch.js:1229-1233` |
| 3 | 大 JSON 整文件反序列化 | **成立，次因（服务端+前端各一遍）**。每会话整份 `.ui.json` circe 解码→重序列化（服务端）+ JSON.parse（前端），6.8 MB 单会话前端 parse ≈30 ms；7,007 会话累计 18.4 s（无网络下限的 50%）。行级分页（`MaxStoredUiMessages=800` 封顶，`SessionStore.scala:107`）已把单文件控制住，但「一次全要」抵消了封顶收益 | §5.3 |
| 4 | 同步阻塞 IO | **不成立（后端）/ 不显著（前端）**。后端读盘在 `IO.blocking`（`SessionStore.scala:1436`），不占计算线程池；前端拉取本就异步。慢是**总量**问题（0.9 GB × 每查），不是阻塞问题 | `SessionStore.scala:1436-1441` |
| 5 | 前端一次性渲染过多结果卡 | **不成立（消息流）/ 有条件成立（媒体网格）**。消息结果渲染 50 行/批懒渲染，实测瞬时（459 DOM 节点）；但**类型分片 tab（图片/文件/链接）的媒体网格是一次性全量渲染**（`renderMediaGrid` `chatSearch.js:1947-1987` 无分批），会话多+条目多时有卡顿面。当前会话档实测 9 张卡 199 ms——量级尚可，属「潜在欠账」非今日主因 | `chatSearch.js:1947`；§5.6 |
| 6 | 首查冷 vs 二查热差异 | **不成立（网关内存缓存已兜住服务端）**。单会话 history 冷 69.7 ms / 热 43-55 ms（差 1.3×）；但**前端零复用**：二查照样重拉全部 7,007 会话（237 s vs 227 s，无改善）。热/冷差异在真实痛点里可忽略 | §5.7 |

### 3.3 归因结论

**慢在哪一段**：95%+ 在「前端把整库当数据库用」——`全部会话` 档每次查询重建全部数据的网络搬运+反序列化+线性匹配。**占大头的是数据量本身**（0.9 GB/查），任何客户端侧小修（提并发数、缓存反序列化结果）都只能砍常数，砍不掉「每查全量搬运」这个量级。次级欠账两条：会话清单的每请求磁盘扫描（0.2-0.4 s，扫 6,509 个文件只为数出未入索引的）与媒体网格无分批渲染（条件性卡顿）。

## 4. 方案：数据层检索骨架（分片索引 + 增量维护 + 结果缓存）

### 4.1 通用骨架（作者令④：固化成数据层方案，不只服务聊天检索）

数据面的检索/浏览场景（聊天记录、文件库、日志、wiki）共享同一张骨架，四个正交组件：

```
┌─ 数据面（源）──────────────┐
│  聊天 .ui.json │ 文件库 │ 日志 │ wiki vault          ← 只读真源，一律不写
└──────┬─────────────────────┘
       │ ①变更钩子（写路径既有锚点，事件驱动）
       ▼
┌─ 分片索引层（可重建的派生物，丢了随时重算）──────────┐
│  <dataRoot>/search-index/<face>.db   （SQLite FTS5）  │
│  分片键 = (类型, 时间片)；每片独立可增量、可丢弃        │
└──────┬─────────────────────┘
       │ ②查询 API（结构化查询语言：分片预过滤 → FTS 匹配 → 排序/摘要 → 分页）
       ▼
┌─ 结果缓存层（查询凭证）──────────────────────────────┐
│  服务端：查询→结果 的 ETag 凭证（复用 HttpCache 语义）  │
│  设备侧：nfFileCache 账本同款（结果体入 Cache Storage， │
│          凭证命中=零重搜，事件失效+TTL 兜底）           │
└──────┬─────────────────────┘
       │ ③消费面（面板/CLI/其他 Agent）——各场景自带 UI，不共享
       ▼
   聊天检索面板 │ 文件库 │ 日志视图 │ wiki 检索 │ stand-recall
```

三条通用纪律（每个接入场景必须满足，即「固化」的验收面）：

1. **索引是派生物，真源永不被写**（既定纪律，`tools/stand-recall` 头注同款：「数据源只读：绝不写 sessions/**，只写 memory-db/**」）。索引损坏 = 删掉重建，无恢复负担。
2. **增量靠写路径钩子，不靠轮询**：数据面在自己的 debounced flush 落盘点发「分片脏」事件；索引层只补变更分片。兜底 = 惰性对账（mtime/行数指纹不一致的分片在查询前顺手重建）。
3. **查询必带分片谓词**：类型片、时间片、会话/范围至少一个；无谓词查询只允许在默认片（近期片）上跑——防止新数据面长大后重演全库扫。

**接口形态**（对内统一，新增数据面 = 注册一个 adapter，不复制一套链路）：

```
SearchIndexAdapter {
  face: String                        // "chat" | "files" | "logs" | "wiki"
  shards(): Seq[ShardId]              // 列出已知分片（ShardId = face+类型+时间片）
  shardFingerprint(shard): String     // 指纹（行数+mtime/内容 hash 前缀）——增量对账键
  buildShard(shard): Iterator[Doc]    // 片内文档流（id/ts/kind/可检索文本/投影字段）
}
SearchIndex.query(face, q: {text, kinds, since, until, scope, page}) → {hits, total, etag}
```

### 4.2 分片模型（作者令①上半：按类型分 + 按时间分）

聊天面的分片设计（其他数据面同构套用）：

| 维度 | 切法 | 理由（数字支撑） |
|---|---|---|
| **类型片** | `message`（user/ai/agent/ask 行）│`tool`（工具行）│`media`（图片/视频条目）│`file`（文件条目）│`link`（链接条目） | 前端五个 tab 本来就分类型检索（全部/图片与视频/文件/链接/日期，`chatSearch.js:76`）；搜文件只查 `file` 片，媒体网格只查 `media` 片——每 tab 的查询面缩小一个量级，且「媒体网格无分批渲染」的欠账被片内结果集天然截断 |
| **时间片** | 按会话 updatedAt 落桶：本周一桶 / 每月一桶（桶边界 = 自然月，月末封口**不可变**，当月桶 = 开口增量桶） | 历史不可变桶永不重建；开口桶只吃增量。检索默认只搜「近期 N 片」，深挖才逐片外扩（分页语义 = 片间游标） |
| **会话键** | 每条文档带 `sid`（会话 id）+ `ord`（行号） | 命中跳转/浮窗打开（`chatSearchFloat.js`）需要 (sid, ord) 定位——现结果模型已带这两个字段，投影直接兼容 |

分片物理形态：**单文件多表**（`chat.db` 内每片一张 FTS 表或一张带分片列的表）起步即可——SQLite 单写者与网关单进程匹配；片目录化（`search-index/chat/<type>/<yyyymm>.db`）留作片数上万后的备选，接口不变。实测数据：cap 2000 字/行 + detail=none 的索引 480 MB（§5.4 表），全 cap 索引 1.29 GB——**磁盘代价与数据面同量级**，可接受且可配（cap/detail 档位见 §4.6 取舍）。

### 4.3 增量维护（作者令①下半：谁维护、怎么不重建）

- **谁维护**：引擎进程内的索引服务（单例，随 GatewayMain 启动）。写路径钩子 = `SessionStore` 既有 debounced flush（`appendUiMessages`→`scheduleFlush`→`runFlush`，`SessionStore.scala:1531,1667`）成功落盘后**追加一步**「标记该会话所属分片脏 + 投递新行」。flush 本来就是批量去抖的（500ms，`SessionStore.scala:278`），索引更新搭同一班车，**零新增写放大风险点**。
- **增量语义**：会话级 upsert（同会话旧行 DELETE + 新行重插 + 局部 FTS 增量），实测单会话（795 行/6.8MB）**545 ms**（§5.4）；典型轮次追加（10-30 行）远小于此。脏分片合并写（同片多会话变更一次刷）。
- **首建与重建**（「重启/压缩后如何重建」的明确答案）：
  - 冷建库 = 一次性 41-56 s（§5.4，同机 Python 原型实测；Scala 实现预计同量级），boot 后台 fiber 跑，**不阻塞启动**；建库期间查询降级走旧全扫路径（行为不变，只是不快）——灰度零风险。
  - 重启后：索引是磁盘文件，**重启零重建**；只做启动对账（逐片指纹比对，错片重建）。
  - 会话删除（`deleteUiMessages`，`SessionStore.scala:1815`）/recall 撤回（`deleteLastUserMessage`）/压缩（`trimUiMessages` 重写文件）：三处写路径都有明确锚点，各补一行「分片脏」标记即可；对账兜底抓漏。
  - 索引版本不兼容（schema 升级）= 删库重建，一次 41-56 s，后台完成。
- **成本上限**：索引体积 ≤ 源数据 1.4×（480MB 索引 / 944MB 源，cap 档）；增量更新 P99 < 1 s；重建吞吐 ≥ 200 行/ms（§5.4 全库 20.5 万行 / 41-56 s ≈ 4-5 千行/s）。

### 4.4 结果缓存与跨设备语义（作者令②③：凭证层 + 网络层）

作者点破的「关系到网络层」正是要害：慢的本质是**每次查询都重做全部取数**，跨设备时还要**再叠加一遍隧道往返**。骨架把「一次查询」变成一个可复用的**凭证（credential）**：

- **服务端查询缓存（凭证铸造）**：`SearchIndex.query` 的结果带 `ETag = hash(face + 规范化查询 + 索引版本)`，索引版本 = 每 shard 一个单调序号（增量更新时 bump）。命中语义直接复用仓内既有的 `HttpCache.conditionalOk`（`src/main/scala/nebflow/gateway/HttpCache.scala:55`，六端点已验证的模式）：`If-None-Match` 命中 → **304，零重搜零重发**；任何分片更新 → 版本 bump → ETag 必变 → 自动失效。**不做内容缓存**（结果体不复制第二份），凭证极小、失效绝对精确。
- **设备侧结果缓存（跨设备复用）**：`nfFileCache` 账本同款语义推广到查询结果（`js/nfFileCache.js` 头注「M2 全数据面推广」正是这个预留）：设备 A 搜过的 (查询, ETag, 结果) 存 Cache Storage；设备 B 打开面板发同一查询 → 服务端 ETag 相同 → **B 命中 A 已经铸造的结果（服务端查询本身也是 O(ms) 索引查询，无需 A 的缓存内容）**；同设备刷新/重开 = 先给本地缓存值 + 后台 ETag 对账（SWR 语义，[[glossary#^swr]]）。「A 设备搜过，B 设备不应重搜」由**服务端索引 + ETag 协商**达成，而不是搬运 A 的缓存——这正是网络层的正解：跨设备要复用的是**查询的权威性**（服务端一次算好，处处 304 确认），不是缓存字节本身。
- **失效策略**：精确失效（分片版本号）为主，TTL 兜底为辅（查询缓存 TTL 可配，缺省与 nf-ticket 同族 30min）；WS 事件（会话写入已推 `historyPage` 页指纹，`src/main/scala/nebflow/gateway/HistoryPageFingerprint.scala`）可在命中打开的页面上做主动失效推送，属可选增强。

| 卡 | 内容 | 验收要点 |

### 4.6 方案取舍（含两个未推荐的备选，作者批方案时对照）

| 方案 | 一句话 | 收益 | 代价/风险 | 工作量估计 | 结论 |
|---|---|---|---|---|---|
| **A. SQLite FTS5 分片索引 + 写路径增量 + 查询凭证（§4.1-4.5）** | 引擎内嵌一个可重建的检索派生层 | 全部会话 3.5min→0.1s（原型实测 §5.4）；跨设备 304；五 tab/其他数据面复用同一骨架；仓内已有两处同构先例（memory-db FTS5、HttpCache） | 新增一个索引组件（体积 ≤1.4× 源、需要重建路径）；SQLite-JDBC 新依赖；CJK 查询需 bigram 影子列（stand-recall 已趟平，同款照抄） | C1-C6 共 5-7 个 delegate 批次（索引服务 2、查询 API+前端 2、媒体网格+多选 1-2、跨设备缓存 1） | **推荐**。最小侵入（零改动既有读写路径语义，只挂钩子）×最大收益（整个数据面通用） |
| B. 会话范围预过滤 + 后端真分页（无索引） | 只把 `limit/before` 光标做实 + scope 收窄，匹配仍逐会话拉 | 实现最小（1 个批次）；当前会话档已达标不用动 | 全库关键词搜索仍是 O(N) 搬运（分页只砍单会话体，不砍会话数）；7,007 会话 × 网络往返的延迟地板仍在分钟级；作者令①②③④全部不满足 | 1 个批次 | **不推荐单做**——但其中「后端真分页」是 C3 的组成部分（光标契约早已定义好，`chatSearch.js:27-32`），作为 A 的一部分落地 |
| C. 前端内存索引（IndexedDB/自建倒排） | 首次全量拉取后前端自建索引，后续查询走本地 | 查询瞬时；零后端改动 | 首建仍要搬 0.9 GB（首次更慢）；每台设备重复建/存 944MB×1.4；**跨设备无凭证**（B 设备照样全量重建，令③不满足）；内存/磁盘压力在设备侧，多开页面各自一份 | 2-3 个批次 | **不推荐**——把成本转嫁给每台设备，与「跨设备复用」方向相反；仅当服务端不可改动时才是唯一解 |

风险与迁移路径（方案 A）：

- **R1 索引与真源不一致**（写钩子遗漏/崩溃窗）：惰性对账兜底（查询前指纹校验脏片）+ `--doctor` 式一致性自检命令（stand-recall 同款）；最坏 = 该片降级走旧全扫路径，**正确性永不依赖索引新鲜度**（索引缺失 ≈ 退化为慢，不退化为错）。
- **R2 CJK 分词**：FTS5 unicode61 对中文退化为整句 token——**仓内已有解**：`tools/stand-recall` 的「CJK bigram 影子列 + 同变换查询」路线（xerj 同款，头注有完整论证），照抄即可；本档 §5.4 的中文查询实测（「检索」5.8ms top50）就是 bigram 变换查询跑出来的。
- **R3 新依赖（SQLite JDBC）**：单文件、零服务、Apache 2.0；备选降级 = 纯 Scala 内存倒排（效果同、重建慢、无 FTS5 rank），接口不变可替换。
- **R4 迁移/共存**：新 API 与旧全扫路径并行一个观察期（前端特性开关），旧路径保底可回退；索引目录独立于 `sessions/`，删目录即完全卸载。
- **R5 隐私边界不变**：索引只在本机 `<dataRoot>/` 内，不新增任何外发面（查询凭证 ETag 也不出设备——跨设备共享的是同一台服务端）。

## 5. 实测附录（测量方法与复现）

### 5.1 环境
本机（M 系列 MacBook Pro，APFS），Nebflow 引擎运行中（gateway 127.0.0.1:6138，2026-10-29 17:40-18:05 采样），数据 = §2 规模。所有脚本一次跑完，无人工干预。

### 5.2 会话清单两腿对比（curl 计时，`%{time_total}`）
`GET /api/sessions`（索引-only）= **7.3 ms / 160 KB**；`GET /api/sessions?includeUnindexed=1`（磁盘扫描）= 200-443 ms / 1.16 MB，返回 7,006-7,007 个会话。慢因 = `listSessionsIncludeUnindexed` 每请求 `os.list` + 逐文件 stat（`SessionStore.scala:766-784`）。

### 5.3 全库扫描下限（纯本地复算，零网络）
脚本读全部 6,513 个 `.ui.json` → `JSON.parse` → 抽可检索文本 → `includes()` 匹配：**端到端 37.1 s**（读盘 6.7 s + parse 18.4 s + 抽取匹配 12.0 s），产出 205k 行 / 7.0 亿字符 / 「delegate」64,917 命中分布 3,747 会话。这就是「全部会话」档的**数据量决定的地板**——实际面板因网络往返放大到 210-237 s。
复现：`node /tmp/probe_fullscan.mjs`（脚本体见会话报告附档）。

### 5.4 SQLite FTS5 原型（同一份真实数据）
Python + 系统 SQLite 3.51 原型（`probe_fts2.py`/`probe_fts3.py`，表结构 = `messages` + FTS5 `content=` 外部内容表 + `idx_msgs_sid_ts`）：

| 变体 | 建库（parse+index） | 库大小 | 查询「delegate」count/top50 | 「检索」top50 | 增量（单会话 795 行 upsert） |
|---|---|---|---|---|---|
| 全文本 | 7.7 s + 41.3 s | 1,294 MB | 1.5 ms / 150 ms（热页缓存） | 10.5 ms | 545 ms |
| cap 2000 字/行 | — | 549 MB | 5.3 ms / 107 ms | 19.2 ms | — |
| cap 2000 + detail=none | 14.4 s | 480 MB | 1.8 ms / 828 ms（rank 慢，适合 count 面） | 15.6 ms | — |

结论：**查询毫秒级、增量亚秒级、建库分钟级一次性**；索引体积可调（cap 档 480-550MB）。中文查询（bigram 变换）与英文同样毫秒级。生产实现再加「warmup 后常驻页缓存」只会更快。

### 5.5 分页参数被忽略（实证）
`GET /api/sessions/<最大会话>/history`：无参数 6.96 MB / `?limit=100` 6.96 MB / `?before=…&limit=100` 6.96 MB / `?after=…&limit=100` 6.96 MB——**四种请求返回字节完全相同**（`SessionStore.getUiMessages(sid,0,0)` 硬编码全量，`SessionRoutes.scala:76`）。前端光标契约（`chatSearch.js:27-32`）早已定义好，只等后端兑现。

### 5.6 前端渲染面（活体，headless Chromium）
当前会话档搜索：88-151 ms 全链路（含 fetch/parse/匹配/渲染）；结果 50 行 = 380 DOM 节点，瞬时完成。`包含卡片行`时另有 `.search-result-card` 内联卡体（iframe）面，当前规模未见压力。媒体网格（文件 tab，9 卡）199 ms——**一次性全量渲染**（`renderMediaGrid` `chatSearch.js:1947`）在当前量级够用，跨会话条目上万后需要 C4 的分批腿。

### 5.7 慢打字放大（活体，PerformanceObserver 插桩）
逐字输入 "delegate"（每键间隔 500ms > 300ms 去抖窗）：**8 次按键 = 8 次 `/history` 全量请求 = 53.1 MB 解码字节**（当前会话档）。每次检索 = 整份会话再拉一遍——前端无结果缓存、无「查询中合并」、无行级缓存。全部会话档按同节奏 = 8 × 7,007 请求（实践中被 seq 竞态取消大半，但每个存活查询都重新扫库）。

### 5.8 既有资产核对（复用面）
- `tools/stand-recall` + `~/.stand/memory-db/memory.db`：主 agent 会话的 FTS5 检索库已在产（12,578 消息/31 MB），查询 P95 < 250ms（含进程启动）——**分片索引的查询形态仓内已验证**；差异面 = 它只收主 agent 会话（语料口径收紧）、CLI 形态、无凭证层；骨架 A 是它的多数据面推广 + 引擎内嵌化。
- `HttpCache.conditionalOk`：ETag/304 小刀，六端点在产（本机实测 304 往返 ≈2ms，v1 §A.1）——凭证层直接复用。
- `nfFileCache`：设备侧内容账本（Cache Storage + LRU 分桶 + 事件失效 + TTL）——结果缓存层直接复用其机制。
- `HistoryPageFingerprint`：WS 页指纹已在产——主动失效推送的现成载体。

## 6. 验收条件（方案确认后实施批的判据，作者批方案时对照）

冒烟红线（最先跑，失败即停）：源目录 `~/.stand/sessions/**` 零写入（前后 hash 快照比对）；旧检索路径行为不回归（当前会话档结果一致性抽查 10 组关键词）。
端到端：「全部会话」搜「delegate」，面板打开→首行落 DOM P95 < 500 ms（基线 210-237 s）；慢打字 8 键解码字节 < 5 MB（基线 53.1 MB）。
后端：单会话追加 → 索引更新 P99 < 1 s；索引删除后查询自动降级不报错；重启后零重建（指纹对账日志为准）。
跨设备：同查询二次请求返回 304（服务端日志零重算）；会话新增后同查询 ETag 变化并 200。
自查清单逐条 PASS/FAIL + 证据路径；实施批交 QA 验收（nebflow-qa 域，非本档范围）。

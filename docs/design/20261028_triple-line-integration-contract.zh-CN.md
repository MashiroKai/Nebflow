> - **effect oracle（效果基准）**：主线的行为（对同一输入的可观测效果）是复刻线对拍的标准答案；复刻线只对效果、不读实现，单向只读主线仓（基线B §1.1）。
> - **cap 服务**：主线的后端微服务（llmgw/identityd/agentd/permd 等 14 个）；triple-star 用 Rust 同名复刻了这 14 个（审计稿 §1.3、§1.6）。

> - **MCP**（Model Context Protocol）：把外部工具/数据源以标准协议接给 agent 的机制；主线机制代码在位（`src/main/scala/nebflow/core/mcp/`），dbm 自带 31 工具的 MCP server（基线A §3.2）。
> - **fail-open / fail-closed**：失败时「默认放行/按默认假设继续」叫 fail-open，「显式拒绝、不静默降级」叫 fail-closed。

## 1. 背景与愿景对齐

**本章一事**：说清主线的愿景与四个现役缺口，逐格对应 triple 线手里有什么——回答「为什么结合、结合能换来什么」。

### 1.1 主线愿景与现状

主线的自我定位是「self-hosted AI agent 编排平台：所有工作汇到一个入口，由平台把任务派发到 agents、项目与设备」（README.md 开篇；口号「One entry. Every agent.」）。落到今天的产品事实：单个自包含 JAR（需要 Java 21+ 环境），浏览器即工作台，任务以 DAG 节点链在 Flow Map 上派发执行（README.md「Features」节）。这个愿景隐含两个承诺——**人人可部署**（不该要求用户先懂 JVM 工具链）与**随处可用**（不只在装好了开发环境的这台机器上）。

### 1.2 四个缺口

以下是主会话批内盘点的四个现役缺口（本文前提，非审计稿结论），每个缺口的事实基底均有仓内锚点：

| # | 缺口 | 现状事实（锚点） |
|---|---|---|
| G1 | **部署重** | 部署＝自备 JDK 21+／Scala 3.5.2 环境跑 JAR（README.md 徽章与正文），构建发布链走 sbt（`build.sbt`）；没有面向普通用户的一条命令安装器 |
| G2 | **安装零工具** | 主线无包管理器、无 install CLI；用户拿到的是「一个 JAR＋一份手工配置」 |
| G3 | **MCP 零实跑** | 主线 MCP 机制代码完整在位——客户端/管理器/工具闸（`src/main/scala/nebflow/core/mcp/`（McpClient/McpManager/JsonRpc）、`src/main/scala/nebflow/core/plugin/PluginMcpManager.scala`、`src/main/scala/nebflow/core/McpToolGate.scala`）——但尚无一个真实外部 MCP 服务被挂载实跑验收（批内盘点结论） |
| G4 | **多设备算力分摊无服务器侧形态** | 主线方向是 P2P 设备腿＋规则放置调度（NebLink 注册表/租约：`src/main/scala/nebflow/neblink/`；设计稿 `reports/20261022_194019_multi-device-compute-design__delegate-nebflow-1c1590ea/` 已合入主线 284cd6f5，见基线B 报告头），**中心化服务器侧**（多租户、瘦客户端）没有现成方案（基线B §0：跨机放置是 C2 的领地，服务器形态不在其内） |

### 1.3 triple 线资产逐格对应

triple 线是一条有纪律的分发工程而非散装仓：依赖方向严格单向 tpm → stand-app → triple-images → triple-star（＋主线 front 构建），三层 digest 钉扎贯穿全链（审计稿 §2）。它的资产对四个缺口的覆盖：

| 缺口 | triple 线对应资产 | 成熟度（审计稿 §3③） | 结合前提 |
|---|---|---|---|
| G1 部署重 | **triple-images** 17 张真镜像（front＋14 个同名服务＋star-dev＋star-onelook，后两者为 amd64+arm64 多架构）＋**stand-app** 组合包（front＋14 服务逐 digest 钉扎＋verify.py 全量重算） | 镜像库成立（第 3 位）；⚠️ host-overlay 缺口：镜像不能直接 docker run，已用 debootstrap 底座实测 15 容器全起【转引 final-arch §3.1】（审计稿 §1.4） | 补 base rootfs（路线图①） |
| G2 安装零工具 | **tpm**：用户第一个下载的 CLI，`triple app install stand` 一条命令装起 front+14 微服务 | 薄壳（第 6 位）：122 行 shell＋预编译二进制，registry/lockfile 未落码（审计稿 §1.2、§3①） | tpm 本体逻辑在 triple-star，Phase 2 才补全 |
| G3 MCP 零实跑 | **dbm**：自带 stdio MCP server、31 个工具、20 条 CLI；我方 10-19 实跑 47 测试全绿 | 六仓中单位体量完成度最高的可运行机制仓（第 2 位）（审计稿 §1.5；基线A §3.2） | MCP 无鉴权只可本机挂载（基线A §6） |
| G4 服务器侧形态 | **triple-star 10-24 最终架构方案**：中心化服务器跑 engine/TGS/agent/cap，用户设备只装瘦客户端＋sandbox-creator/sandboxd；Docker→K8s 路线；Phase 0-6 迁移 | 方案完整（517 行设计稿）但「待实施」，未合默认支（审计稿 §1.6） | 属对方未落码工程，须先对齐再依赖 |

独立两仓里还有第二重资产：dbm 的「治理不变量落 schema 级＋写后全量校验回滚」与 kr 的「写入分级＋论证证书（obligation kernel）」是主线没有的角度（审计稿 §3④-3），对应路线图②。

### 1.4 小结

四个缺口里，G1/G2 的解法（镜像＋包管理 CLI）在 triple 线已有真物、只差一步基建；G3 的首个实跑对象（dbm）现成可挂；G4 恰是对方新方案的问题域。**结合不是合并代码——语言异构（Rust vs Scala）、两线独立开发是既定纪律（基线B §2-B）——而是认领角色＋钉接口**。怎么钉，见第 2 章。

## 2. 分层契约（核心章）

**本章一事**：把两条线各自的权责层位、四个接口钉点、依赖方向与变更通知机制写成可执行的契约条款；§2.4 给负面清单防过度耦合。

### 2.1 三层模型：一个大脑，两个面

```
┌─────────────────────────────────────────────────────┐
│ 大脑与行为协议基准：主线 Scala 引擎（本仓）              │
│  · 行为基准：triple-star 自述 main=effect oracle，     │
│    单向只读、零写主线仓（基线B §1.1，proc-branch:39-41）│
│  · 协议权威：/app/v1 等 API 语义的唯一权威              │
└───────────────┬─────────────────────────────────────┘
                │ ① 行为/协议对拍（复刻线消费主线的行为）
                │ ② front 构建（主线 web UI 构建物 → front 镜像）
┌───────────────┴─────────────────────────────────────┐
│ triple 线＝分发面 ＋ 边缘执行面                          │
│  分发面：tpm（CLI 入口）→ stand-app（组合声明+digest）   │
│          → triple-images（唯一镜像库）→ triple-star     │
│          （构建配方），依赖严格单向（审计稿 §2）           │
│  边缘执行面：14 个 Rust 同名 cap 服务复刻（审计稿 §1.6）  │
│          ＋ Linux 底座（eOCI/govd/隔离单元，基线B §1.4）  │
│          ＋ 服务器侧形态（10-24 方案：TGS/sandboxd，     │
│          审计稿 §1.6）                                 │
└─────────────────────────────────────────────────────┘
```

三条分层裁定：

1. **主线是大脑与行为协议基准**。「effect oracle」的含义：复刻线不读主线实现、只对主线**行为效果**（对拍门＝唯一接口）；内核/执行基底主线无对应物，登记 oracle 不适用（基线B §1.1）。这个关系是 triple-star 自己的开支令钉下的，本文只是把它升格为两条线共同的契约前提。现状证明了该关系可运转：复刻线维护 651 件基线的覆盖矩阵、30 轮裁定 325 项，主线一出货数日内对位复刻（审计稿 §1.6）。
2. **triple 线是分发面**。用户侧的部署通路（G1/G2 的解法）整体由复刻线承担：镜像怎么打、包怎么组合、CLI 怎么装，主线不造第二套。分发链的 digest 纪律已在位：应用包钉镜像 digest、catalog 钉 layout 字节哈希、verify.py 全量重算 blob sha256（审计稿 §2）。
3. **triple 线是边缘执行面**。14 个 Rust 同名 cap 服务＋Linux 底座（轻档 chroot/cgroup 与强隔离档 microVM 两档执行单元、govd 水位准入，基线B §1.4）以及 10-24 方案的服务器侧形态（G4 的解法），定位是**边缘**：主线关键路径（大脑、会话、审计、秘密）不依赖它——这与基线B §2-D「C1 对 triple-star 零依赖」的裁定一致，主线永远不会因为复刻线不可用而不可用。

### 2.2 接口契约钉什么（四钉）

「钉」＝写进契约、双方变更时必须遵守的固定点。四个钉点全部是对**既有事实**的升格——每一条在今天的两仓里都已成立，契约只是把巧合变成规则。

**钉一：/app/v1 协议面——语义权威在主线。**
triple-star 复刻的 /app/v1 协议与 triple-app/v1 组合协议，语义来源就是主线 API（审计稿 §3②：「协议面（/app/v1、triple-app/v1 组合协议是我们 API 语义的复刻）」）。契约含义：协议语义的**主线是唯一权威**，任何分歧以主线仓为准、以复刻线对拍门为验收；复刻线扩展自有协议（如 launcher.yaml 的 triple-launcher/v1，审计稿 §1.2）不得占用主线协议命名空间。

**钉二：front 构建物来源——可追溯到主线构建。**
front 镜像的内容就是主线 web UI 的构建产物重打包；其 digest 是**镜像摘要而非 git commit**——2587dd66/9b364c52 在双方 git 仓里都不存在对应提交对象，来路只能靠文档声明（审计稿 §3②、§4 表末行）。契约含义：stand-app 的组合声明必须记录「主线 tag/构建号 → front 镜像 digest」的映射，让每个 front 镜像都能回答「你打自我主线的哪次构建」，杜绝来路不明的 front。

**钉三：digest 钉扎纪律——只增不覆写。**
现状已严格执行：manifests/stand.yaml 的 URL 必带 sha256（审计稿 §1.2）、14 个服务逐 digest 钉扎（§1.3）、镜像库 verify.py 全量重算（§1.4）。契约含义：任何分发物变更**只允许新增 digest、不允许覆写旧 digest**——旧版本永远可回滚、可审计；配合钉二形成完整的「主线构建 → 镜像 → 安装包」证据链。

**钉四：版本耦合——stand-app 版本跟主线 tag。**
现状已经对齐：stand-app 版本 2026.10.21-beta.1 与主线 tag `v2026.10.21-beta.1` 同名同口径（审计稿 §1.3「与我们主线的版本日期口径对齐」；主线 `git tag` 实有 v2026.10.21-beta.1，当前 VERSION=2026.10.26-beta.2）。契约含义：主线每打一个 release tag，复刻线发布的对应 stand-app 版本号必须取该 tag（`v` 后段），front 镜像由该 tag 的构建产出——版本号从此不是巧合，是分发面与主线之间的硬耦合点，也是钉二映射的键。

### 2.3 变更通知机制：把「数日内对位复刻」从巧合变机制

**现状**：主线新特性（委派链读面、Teams children、流式重启、20 域 UI smoke）几天内被复刻进 Rust cap 服务并回写 E2E 证据（审计稿 §1.6「gaps 合并」实质）。但这靠的是复刻线自己盯主线仓的**自觉**：没有「主线变了 → 复刻线何时必须跟上」的承诺，也没有滞后的计量。

**机制设计**（本文提案；零新基建，全部落在既有工件上，需安齐确认后生效——附录议程第 1 条）：

1. **对拍锚点唯一化**：主线 release tag 是复刻线唯一的对拍新基线（与钉四同键）。主线不需要知道复刻线内部任何事，通知内容就是公开的 tag＋release notes。
2. **协议面变更显式标注**：主线在 release notes 中标注「协议面/效果面变更」条目（哪些 route、语义、行为变了）。这是主线侧唯一的新增动作——写清楚哪次变更动了对拍面。
3. **覆盖矩阵增量对拍**：复刻线在收到新 tag 后的下一个门禁轮内，对覆盖矩阵（已有 651 件基线，审计稿 §1.6）做增量更新，把「数日内对位复刻」变成**可计数指标**（未对拍件数、滞后轮数）。
4. **单向纪律不破坏**：整个机制只有「主线发布公开事实、复刻线消费公开事实」一条信息流，双向零依赖——守两线独立开发纪律（基线B §2-B 纪律注）。

**效果**：复刻滞后从不可见变成一个每周随 tag 走的数字；主线协议演进再快，复刻线的跟进也是义务而不是人情。

### 2.4 契约不钉什么（负面清单）

- 不钉**实现语言/代码结构/构建工具链**——Rust 与 Scala 各自保留（语言异构是既成事实，审计稿 §3②）。
- 不钉**源码互引**——两线代码不进对方仓；主线取用 triple 线代码属跨线引用，交作者逐案裁定（基线B 开放项 O4）。
- 不要求主线**感知复刻线存在**——主线对 triple 线零依赖、零运行时链接（基线B §2-D：C1 对 triple-star 零依赖）。
- 不钉**执行面内部形态**——govd/沙箱/隔离单元怎么演进是边缘执行面的内政，主线只关心接口钉点与行为效果。

## 3. 四层结合路线图

**本章一事**：给出四个可执行的工作层，每层说清做什么、凭什么、验收什么。顺序即依赖：①②是近期可动手层，③是文档先行层，④是对齐驱动层。

### 3.1 第一层：分发收编（治 G1+G2）

**做什么**：把 triple 分发链收编为 Stand 的官方安装路径，三件事——
1. **CI 化**：主线出包后自动同步 triple-images 配方。现状的 sync 是手工脚本（`sync-from-stand.sh`/`sync-from-triple-star.sh`，审计稿 §1.4），要变成主线 release 流水线的下游步骤，与钉四版本耦合同拍触发。
2. **补 base rootfs**：现有 OCI 层是 host-overlay（不含 libc/`/bin/sh`），不能直接 docker run【转引】；debootstrap minbase 底座＋overlay 已实测 15 容器全起（审计稿 §1.4）。把底座进配方，镜像成为真正「可部署镜像」。
3. **验收一条命令**：效果＝用户 `triple app install stand` 一条命令在本机部署 front+14 微服务（triple 线自己的目标口径，审计稿 §3①）。

**凭什么**：分发链纪律（三层 digest 钉扎）已在位（审计稿 §2）；镜像库与组合包结构完整（审计稿 §1.3/§1.4 判语「合格的应用包仓」「确定性 catalog 纪律好」）。

**验收**：从主线 tag 到 `triple app install stand` 可跑通，全程自动、无人值守；镜像可被外部 docker 直接运行。

**边界**：配方在对方仓，需安齐侧配合；USTC 镜像仓权限未确认（基线B O2）；host-overlay 现状是【转引】读数，动工前按第 4 章第 1 条复跑核实。

### 3.2 第二层：机制借将（治 G3，兼收两枚机制仓）

**做什么**：两枚独立机制仓以「模式借将」进主线工具链，不引源码（守基线B O4 纪律）。

**(a) dbm 作首个 MCP 插件——直接治 G3。**
- 凭什么：主线 MCP 机制代码在位而零实跑（第 1 章表 G3）；dbm 自带 stdio MCP server、31 个 `dbm_*` 工具、错误码带 hint/next（基线A §3.2）；挂载方案已有现成稿——基线A §8 方案 A「MCP 挂载（推荐起步）」：`DBM_ROOT` 指向 Stand 数据目录、`DBM_IDENTITY=user:stand`、治理包从 User.md/Soul.md 脚手架生成，迁移成本「低」；多身份天然对应主线多角色/worktree 场景（`agent:<name>`、`worktree:<branch>`）。
- 安全边界（硬约束）：dbm MCP 无鉴权，stdio 本机信任模型可接受，**不可**暴露到网络/多租户 MCP 网关（基线A §6）——挂载形态必须守住这一条。
- 效果：G3 从「零实跑」变「一个真实生产级挂载」；主线记忆面获得「冷记忆库」形态（基线A §8 建议混合态：扁平 md 当热记忆，dbm 当冷记忆库，batch 写＋定期 export）。

**(b) obligation kernel 引入 delegate-judge 判定硬化——治 fail-open。**
- 现状：主线 delegate-judge 的失败语义是两层判定全败 ⇒ None ⇒ **fail-open** 按「文件变更」处理，以保分支纪律与合并队列资格（`src/main/scala/nebflow/llm/decision/DelegateJudgeMachine.scala:29`「两层全败 ⇒ None（fail-open——spawn 腿两层全败＝按判是」、`:85`「failing open to file-changing (branch discipline + merge-queue eligibility preserved)」）。语义本质：**不知道时，当作是**。
- kr 资产：obligation kernel 把一个 claim 编译成证明 DAG，Judge 产出 verified/supported/contradicted/**insufficient** 四档证书（审计稿 §1.1）——关键在第四档：「证据不足」是显式结论，而不是降级为默认真。
- 借法：在主线 judge 输出面引入四档证书语义（新增 insufficient 档＝显式挂起，交人工/上游仲裁），替代「None 即按判是」的静默 fail-open；这是**协议语义借将，不是代码引入**（kr 是 Python 单 commit 原型，审计稿 §1.1，不满足入仓条件）。
- 效果：fail-open 的语义根从「默认放行」改为「显式存疑」，同时保留原 fail-open 的分支纪律（挂起≠拒绝派发，是带标记的放行）。

**验收**：(a) 一个真实 MCP 服务在主线会话中实跑通过（含工具调用与失败路径）；(b) judge 输出面四档语义落地并有测试。

### 3.3 第三层：标准合流（词表与命名）

**做什么**：两件事，都是文档批可启动的。

**(a) sandbox grant 与 permd 词表对齐。**
triple 线的 triple-sandbox/v1 模型（app 发 request → 用户签 grant → 本地 sandboxd 强制；device-scoped、fail-closed、Seatbelt/Landlock/AppContainer 三后端）与我们主线权限面 permd/PermShield 高度同题（审计稿 §3④-4；主线权限模型锚点 `src/main/scala/nebflow/core/permissions.scala`）。动作：建**一份 grant 标准草案目录**，两线词表逐概念对照（request/grant/scope/enforce ↔ 主线权限语汇），目标是两线共指一套概念，避免各造一套词表。起草与存放仓在附录议程第 3 条与安齐商定。

**(b) 命名划界。**
现状是「Stand」一名两线：triple 线 10-21 把产品/镜像/CLI 全部改名 Stand（审计稿 §1.6 REBRAND；§3④-2），而 front 镜像打的又是我们的 UI 构建——对外任何场合都需要区分「主线 Stand」与「triple 线 Stand」。划界方案：**「Stand」产品名归主线；triple 分发物走 tpm/triple 品牌**（CLI 叫 triple、镜像叫 triple-images，分发物不占用 Stand 名）。顺带一并定 dbm 包名 `nebflow-dbm` 挂主线旧产品名的归属（审计稿 §1.5）——若 dbm 纳入主线工具链（3.2(a)），更名事宜同批谈。

**验收**：一份对照目录＋双线 README 各自的命名声明。

### 3.4 第四层：路线合流（治 G4，需对齐驱动）

**事实面**：triple 线 10-24 最终架构方案＝中心化服务器＋瘦客户端＋sandbox grant＋多租户，Docker→K8s 路线，Phase 0-6 迁移（审计稿 §1.6）；该方案未合默认支、拆仓未执行（同节注）。我们这边的多设备算力分摊＝P2P 设备腿＋规则放置（NebLink/C1/C2，基线B；设计稿已合主线 284cd6f5），没有服务器侧形态（第 1 章 G4）。

**裁定时效**：基线B（10-22）裁定两线「互补不竞争」，依据是当时 triple-star 跨机面 P4 未落码、无跨机调度（基线B §0、§1.3）；10-24 方案把对方整条线转向了中心化服务器——与我们 G4 的问题域显著接近，审计稿 §3④-1 已将其列为「方向撞车风险重估（最要紧）」。

**动作**：在对方 **Phase 1（四仓拆分）落地前**重估 10-22 裁定，把它升级为第 2 章的分层契约——不是竞争也不是含糊的互补，而是：**服务器侧执行形态由 triple 线承接（它的 10-24 方案就是我们 G4 的服务器侧），跨机放置与调度的语义权威仍由主线定义**；具体分工表（谁的调度器、谁的多租户、谁的沙箱标准）在附录议程对齐后产出。

**顺序纪律**：先谈后动。对方 Phase 1 启动前是窗口期（审计稿 §3④-1「建议在他们的 Phase 1 落地前重估分工」）。

## 5. 附录：对安齐对齐议程

**本章一事**：与安齐（triple 线作者）下次对齐的六条议题。本附录可单页撕出独立使用；每条给「现状 → 要对齐什么 → 我方倾向」。

> 使用说明：六条按优先级排序；第 1 条是其余五条的总纲。会前把本页发安齐预读。

**议题 1｜分层契约确认**（总纲）
现状：main=effect oracle 是 triple-star 开支令自钉的单向关系（基线B §1.1）；本文第 2 章把它扩为「大脑／分发面／边缘执行面」三层契约＋四钉（§2.2）＋变更通知机制（§2.3）。
要对齐：确认三层归位与四钉有效；变更通知机制第 3 条（覆盖矩阵增量对拍窗口）需要他承诺。
我方倾向：机制零新基建，只在既有工件上加承诺；先小范围（下一两个主线 tag）试运转再固化。

**议题 2｜命名划界**
现状：「Stand」一名两线（审计稿 §1.6、§3④-2）；dbm 包名还挂着 nebflow- 前缀（§1.5）。
要对齐：「Stand」产品名归主线；triple 分发物走 tpm/triple 品牌；stand-app 过渡期命名与 dbm 更名。
我方倾向：分发物改名成本低（多为 manifest/README），宜早不宜晚；改名不破坏 digest 钉扎（钉三：只增不覆写）。

**议题 3｜sandbox 词表**
现状：triple-sandbox/v1 与主线 permd/PermShield 高度同题（审计稿 §3④-4）。
要对齐：grant 标准草案目录由谁起草、放哪个仓、两线词表对照的范围（先 request/grant/scope/enforce 四个核心概念）。
我方倾向：一份目录两线共签；主线贡献 permissions.scala 的既有语汇（`src/main/scala/nebflow/core/permissions.scala`）。

**议题 4｜服务器同环境**
现状：对方「测试机已有 Docker」（审计稿 §1.6）；我们东风云生产迁移推进中（基线B §2-C/O1）；是否同环境未确认（审计稿 §3④-6②）。
要对齐：两线服务器部署是否同一台/同一网段；端口、资源、镜像仓（USTC，基线B O2）怎么划分。
我方倾向：若同环境，出一份端口/资源分配表再部署；若不同，各走各的探针清单。

**议题 5｜四仓改名与 stand-app 归档时点**
现状：10-24 方案要拆成 triple-engine/TEL/tpm/triple-image 并归档 stand-app（审计稿 §1.6），未执行；本方案 3.1 层的分发收编需要知道对接面是 stand-app 还是 engine。
要对齐：拆仓与归档的时间表；归档时既有 digest 钉扎与 verify 通路如何保持可验证。
我方倾向：stand-app 在归档前维持 digest 纪律不变；归档动作本身写进钉三的证据链（归档≠失效）。

**议题 6｜dbm＋kr 纳入主线工具链的范围**
现状：dbm 挂载评估已有稿（基线A §8 方案 A，MCP 挂载起步成本最低）；kr obligation kernel 与主线 delegate-judge fail-open 硬化的接口已在 3.2(b) 勾出。
要对齐：dbm 作首个 MCP 插件的挂载范围（仅本机 stdio，基线A §6 边界）；kr 只借「四档证书」协议语义、不引代码的口径确认（基线B O4）；两仓后续迭代节奏（dbm/kr 各自单 commit 后零迭代/占位实现，审计稿 §1.1/§1.5）。
我方倾向：dbm 先挂、跑两周真实会话再谈深化；kr 的 judge 协议语义先在主线侧独立实现验证。

## 一、结论（先行）

**两个案例是两个独立缺陷，共享同一个放大器。**

- **案例 A 根因 = 触发链同步阻塞串行化**：`settleDeps` 沿 `traverse_` 逐个调用 `startNode`，而 `startNode` 直到被启动节点**整个会话跑完**才返回（内部 `IO.race(resultDeferred.get, …)`，NodeEngine.scala:505）。于是「同一上游的 N 个 deps 依赖者」被压成深度优先串行链：H1 完成后 H5→H4→H3→H6 依次独占执行（日志实证：每个节点 spawn 时刻 = 前一节点 completed 时刻，间隔 10–17ms）。H2 排在队尾第 5 位，预计等到 ~20:00 才轮到——在 19:31 观察点上它已 pending 2h14m，**外观即「pending 永动」**。H2/H6 都没有丢失触发，只是被串行队列吞掉了。
- **案例 B 根因 = 孤儿 barrier + 触发一次性丢失**：收口C 与 追加-project-memory 先后都声明了 `in=[收口B]`，而 `in` 接线的实现是**覆写上游单值 out 边**（NodeTools.scala:664-668）——后声明者（追加）夺走 `收口B.out`，先声明者（收口C）的 barrier 永远等不到投递。收口C 唯一一次重估机会（15:36:41 追加完成 → `settleDeps` → `startNode`）被 in-barrier 闸门**静默吞掉**（NodeEngine.scala:194，无日志无状态无信号），此后全系统再无任何机制会重访该节点，滞留 96 分钟直到 Nebula 人工自查（16:03 Schedule）→ 救场 NodeEdit（16:17:35）才续命。
- **共享放大器**：pending/wiring 是非终态，但没有**周期性资格重估回扫**、没有**停滞看护**、没有**异常留痕**。任何触发层缺陷（串行化延迟、孤儿 barrier、投递丢失）都会退化成「无终态、无信号、无人知」的永久悬挂。TaskStuckWatcher 只覆盖有活会话的 running 节点（TaskStuckWatcher.scala:67），pending/wiring 无会话 → 全盲。

对接在飞批（n-e5159e2f）的一句话建议见 §6.3。

### Q1 「依赖满足 → 会话 running」完整路径与逐环节退出点

### Q2 资格评估的触发时机：只有事件驱动，零周期重估

`startNode` 的全部调用方（事件驱动，一次性）：
1. NodeEdit create：入口自动启动（NodeTools.scala:732-734，runDetached）、D1 已完成上游补投递（:697-707）、D1-deps settle（:713-722）；
2. NodeEdit edit：blocked 重激活补投递+结算（:1115-1133）、追加上游补投递+barrier 复查 fix-b（:1156-1185）、D1-deps settle（:1192-1200）、completed 改接重投（:1138-1146）；
3. 上游完成：deliverOut（NodeEngine.scala:843-868，:865 调 startNode）、settleDeps（:611-619）；
4. 上游失败：deliverFailed collect 结算（:870-898）／合并转 blocked（:882-883）；
5. release 放行传播（:777-782）／deliverOutTo（:135-158）。

**没有任何周期性/补偿性重估**：TtlTick 30s 周期（ProjectActor.scala:195-201、220-233）只做 `redeliverUnconsumedNebulaResults`（out=Nebula 结果补投，NodeEngine.scala:1013-1052）+ TTL 归档 sweep，**不扫 pending/wiring 的启动资格**。**spawn 失败无重试**：failNode 即终态；`NodeDef.retries/maxRetries`（ProjectTypes.scala:95-96）落库展示但**无任何消费方**——声明了却未接线的字段。启动挂载也无对账：`mount`（ProjectActor.scala:74-123）不复核持久化的非终态节点（重启后 running 节点成僵尸，只能人工 NodeEdit abandon 收殓）。

### Q3 并发启动窗口与「worktree 在、会话无」

- **同批多依赖者是串行循环，不是并行 spawn**：`settleDeps` 用 `traverse_`（IO 语义=顺序 flatMap，NodeEngine.scala:611-619），且每个 `startNode` 同步等该节点跑完（:505）。案例 A 日志时序（§2.1）为直接实证。deliverOut/deliverFailed 的下游启动同样同步阻塞（:865/:894）——上游完成 fiber 会被下游整个会话质押（H1 的完成 fiber 从 17:43 被质押到 H6 完成为止，全链嵌套在同一个 fiber 上）。
- **worktree 与会话天然解耦**：worktree 在 NodeEdit 创建时即时建好（NodeTools.scala:481-497，裁决 a fail-fast），会话在 startNode 时才 spawn。「worktree 在、会话无」= 该节点处于 pending/wiring 且未获触发/还在排队——案例 A 五个 worktree 17:17 全建、H2/H6 会话 19:27/19:35 才来，正是此解耦+串行队列的合成观感，**无需锁竞争假设**。
- **worktree 创建本身无锁但有兜底**：`createWorktreeFor` 用 `os.exists` 探名+`git worktree add`（NodeTools.scala:490-497），并发同名创建存在理论竞窗，后果是后到者报错拒建节点（fail-fast、无半态），且分发器单会话 turn 内串行，实险低——footnote 级。
- **真正要警惕的并发窗口在 startNode 自身**：翻转 mutate（:390-397）**无 status 前置守卫**（不管 fresh 是什么状态都覆写为 Running），双 fiber 同时通过①②③闸门（都读到陈旧 Pending）即可双 spawn（第二个 spawn 覆写 running 表与 startedAt）。现状被「调用方恰好串行」掩盖；**若按 §6.1 把触发链并行化，必须先补 CAS 式翻转守卫**（`fresh.status == Pending || Wiring` 才翻转 + mutate 内返回「是否本 fiber 完成翻转」标记）。

### Q4 案例 A 与案例 B：独立缺陷，同族放大器

- **A = 吞吐/时延缺陷**（触发全部到达，但被串行化拖成小时级排队，外观似永动）；**B = 触发丢失缺陷**（孤儿 barrier + 闸门静默吞掉唯一重估时机，真·无触发）。机制不同。
- 同族之处：两者都利用了同一个系统盲区——**非终态（pending/wiring/排队中）没有可观测语义、没有看护、没有重估**。A 里排队中的 H2 与 B 里被饿死的收口C 在图上**完全无法区分**（都是无会话非终态），这正是作者把它感知为同一现象的原因。
- B 不是首犯：NodeTools.scala:1158-1164 已记载同型案例 n-219106db（「两个归档 completed 上游在 in 里、deliveredTo 恒空、下游永久等待」），20260903 的 fix-b 只在 **edit 追加边时**补投递——把窗口收窄但没有关死：**上游在边创建之后才完成的孤儿 barrier**（本案）依然无解，只能等下一次 edit 救场。

### Q5 修复方向（最小改动）

#### 6.1 堵串行化（案例 A）——触发链 fork 化

把四个同步 `startNode` 调用点改为 detached fork（复用 NodeTools.scala:187-195 `runDetached` 的既有形态）：
- `settleDeps` 遍历体（NodeEngine.scala:618）：`d => runDetachedFork(s"settle-deps -> ${d.id}")(startNode(d.id))`；
- `deliverOut`（:865）、`deliverFailed`（:894）、`deliverOutTo`（:156）内的 `startNode(targetId)` 同样 fork。

效果：H1 完成后五个依赖者**同时**获得会话（案例 A 中 H2–H6 将在 17:43:46 并行启动）；上游完成 fiber 不再被下游质押；链深嵌套（SOE 风险面）同步消除。**前置硬化（必须同批落地）**：Q3 所述翻转 mutate 补 CAS 守卫（:390-397 加 `fresh.status ∈ {Pending, Wiring}` 条件 + 返回翻转标记，仅完成翻转的 fiber 继续 spawn，败方走 :398-406 既有回滚路径）——否则并行化会把理论双 spawn 窗口变成现实。fork 后的错误观测沿用 runDetached 的 handleErrorWith 日志形态。

#### 6.2 堵触发丢失（案例 B）——TtlTick 挂资格回扫（settleSweep）

在既有 30s TtlTick（ProjectActor.scala:220-233，已挂 `redeliverUnconsumedNebulaResults` 同位点）追加 `engine.settleRunnableSweep()`：
1. 扫活动区 `status ∈ {pending, wiring}` 节点；
2. **孤儿 barrier 自愈**：对 in 中「completed+有 result+deliveredTo 未记」的上游逐个 `deliverOutTo`（deliverOutTo 自带 deliveredTo 去重，幂等；语义=把 NodeTools.scala:1156-1185 的 fix-b 补投逻辑从「仅 edit 时」提升为周期性）；
3. barrier/deps 均满足者调 `startNode`（闸门全在 startNode 内，幂等；经 6.1 的 fork 化不阻塞 tick）。

# 合并节点设计指南（v1 · 试点版）

心智模型（一句话）：有 WT 必有合并节点；合并节点的 in 边集 = 合并账本。

## 1. 创建时机
分发器每建一个「产出 WT 的实施节点」，同批次就要有合并节点承接——建 WT 节点和「建合并节点/把自己接进既有合并节点」是同一个动作的两半，不许拆开记忆。

## 2. 依赖即账本
合并节点 in=[本窗全部 WT 节点]，barrier 语义天然保证全部 completed 才开跑；in 边集就是「该合什么」的显式清单——不靠会话记忆、不靠 Nebula 记账，忘不掉。

## 3. 生命周期规则（作者 2026-09-07 裁定）
- 合并节点未触发（pending/wiring）→ 新 WT 完成后 NodeEdit 把自己接进同一合并节点的 in；
- 合并节点已触发（running/completed/blocked）→ 新 WT 配新合并节点；
- 禁止向 running/completed 的合并节点追加 in 边。

## 4. 合并节点任务模板（固定五段）
① 前置核对：main HEAD 快照 + in 边集分支 tip 清单 + 各支基线 vs 当前 main 的 rebase 评估；
② 顺序合并：--no-ff 逐支，每支合完跑该支快速门禁（compile+定向测试）；冲突=双方语义并存手工收敛，收敛不了→BLOCKED 报告（禁 force 禁跳支）；
③ 全量快速门禁收口；
④ 清理对账：逐支 worktree remove + branch -d（零领先校验）+ MERGE_HEAD/暂存区收口核查（防假 completed 污染后续批——20260907 前既有教训）；
⑤ 报告：合并清单表（分支×commit×门禁数字）+ 清理对账 + 0 push 声明，out→Nebula（验收窗转作者）。

## 5. 失败语义
上游 failed → 合并节点 blocked（既有 merge 语义）——「不会忘记」的反向保障：缺谁卡谁。处置三选一：摘边缩窗（报告留痕）/ 修复该批 / 整窗推迟。

### 5.1 死锁逃生形态修正（2026-09-07）

NodeEdit 的 in 边**只追加、不可移除**（`in +=`）。合并节点被 failed/cancelled 上游 barrier 死锁时，**「改合并节点 in 换掉坏上游」不可行**（in 只能加不能减）。正确逃生两形态：

- **① 改上游 out**：把 failed/cancelled 上游的 out 改接 Nebula（节点元数据可更新，从 barrier 摘除）后重激活合并节点；
- **② abandon 重建**：abandon 该合并节点（留审计）+ 新建承接合并节点（in 接有效上游、out 接原下游）。

「真实交付分支」以 git 事实为准（`git log main..<branch>` 非空），勿信节点名/清单名——SBs 批实证：清单内空壳分支、真实交付在清单外分支。

## 6. 边界
per-project 各自合并节点，不跨项目合流；上游重激活重跑时合并节点靠依赖自动继续等它。

## 7. 操作注意（既有 PATTERN）
创建顺序=先上游节点→再建合并节点（带 in）→再补上游 out，规避 wiring 态创建死角；合并节点自身禁 worktree。

## 8. 试点与转正
2026-09-07 21:30 窗=首个试点（9 批 8 支全 in 接一个合并节点）。观察点：接线顺手度/barrier 等待准确性/冲突收敛/清理对账/「新 WT 挂老合并节点」路径（若无场景留待下次验证）。试点通过→蒸馏进任务分发器提示词（定义层 git commit）；未通过→修订本指南再试点。

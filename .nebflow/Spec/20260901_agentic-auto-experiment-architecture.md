## 1. 愿景与定位

### 1.1 两阶段愿景

**阶段 1（agent 化）**：Agent 读取和控制核电子学实验设备（高压电源、DAQ/ADC/FPGA、温控、示波器、束流/放射源），自主执行实验测试，并对采集数据进行分析后发起下一轮测试——形成完整闭环：

```
监控状态 → 调整参数 → 采集数据 → 分析数据 → 下一轮测试
```

解决的痛点：长时间实验（小时-天级）人工盯守、参数扫描机械重复、值守疲劳、人工调参依赖经验。

**阶段 2（具身智能探测器系统）**：构建核实验领域的专用模型——像 StarWhisper 在天文领域那样，让模型**自己识别物理事件**。与天文（大光学图片）不同，物理事件是**波形**：单事件数据小（几百样本量级）但量大（DAQ 自然产生 kHz 以上触发率），标注来源多（触发类型、分析结果、已知信号），作者判断训练比天文容易——本文第 7 章展开这一判断的依据与实现路径。

### 1.2 与 Nebflow 的关系（建议项，待作者裁定）

三种可选定位：

| 方案 | 形态 | 优点 | 缺点 |
|---|---|---|---|
| A. Nebflow 垂直应用 | Nebflow 作为 L1 编排层，实验 agent 跑在 Nebflow 内；设备接口层是独立进程，经 MCP 接入 | 复用 Nebflow 的编排/记忆/skill/值守/审计能力，不重复造轮子；Nebflow 已在实验机常驻 | 实验现场机器可能不跑 Nebflow；聊天式 harness 的长时无人值守需 flow/headless 支撑 |
| B. 独立系统 | 独立 agent harness + 设备层 | 完全自主可控，不依赖 Nebflow 演进 | 编排、记忆、多 agent、审计全部重造，工程量大 |
| C. 实验侧薄 harness | 设备层自带轻量 CLI/脚本执行模式，agent 可选 | 现场无 Nebflow 也能跑确定性自动化 | 缺少 LLM 编排能力，只覆盖「确定性」半边 |

**建议：A 为主 + C 兜底**——设备接口层设计为**独立可部署、协议中立（MCP）**的服务；Nebflow 作为首选 agent host（L1）经 MCP 接入；同时设备服务自带 CLI 与脚本执行模式，实验现场无 Nebflow 时仍可跑确定性自动化与人机同界面操作。这样「实验控制层」不绑定任何具体 harness，恰好呼应 MHS「模型无关、任何 agent harness 可用标准协议访问」的设计原则。

**与博士开题调研的衔接**：开题调研 Track 2 结论——探测器电子学本体（标定、束流测试、健康监控）的 agent 化是明确学术空白，首推「束流测试/标定自主 agent」。本架构可作为该课题的系统骨架，阶段 1 落地的数据管线与轨迹记录同时为阶段 2 与开题课题积累素材（建议项，待作者裁定是否纳入开题）。

### 2.2 各层职责与接口

| 层 | 职责 | 关键接口 | 技术形态（建议） |
|---|---|---|---|
| **L1 Agent 编排层** | 实验协议执行、决策、值守、审计；生成「动作请求」而非直接触达硬件 | 经 MCP 调用 L2 的 tools；调用 L4 分析工具 | Nebflow（建议项）；无 Nebflow 现场退化为 L2 自带 CLI/脚本 |
| **L2 实验控制层** | 设备抽象、能力描述、安全强制、事件发布、授权 | `describe/read/write/subscribe/stop`（见 §3.4）；对外暴露 MCP server + CLI + HTTP API | 独立 Python 服务（建议项，理由：与科学计算/仪器生态一致，见 §3.5） |
| **L3 数据采集存储层** | run 管理、波形落盘、元数据与轨迹记录、分析结果归档 | 采集服务 API；存储格式约定（§6） | HDF5/ROOT + JSONL 轨迹 + SQLite 索引 |
| **L4 分析决策层** | 离线/在线分析：能谱、拟合、质量指标、决策输入 | 分析服务 API（供 L1 调用）；分析结果写回 L3 | Python 科学栈（ROOT/pyROOT）；阶段 2 引入模型 |

**数据流主链路**：L1 agent 决策 → L2 安全门校验 → 下发设备 → L3 采集落盘 → L4 分析 → 结果写回 L3 并反馈 L1 → 下一轮决策。**决策与执行分离**是贯穿全架构的第一原则（借鉴 StarWhisper「VLA 只生成登记动作，确定性程序掌握最终执行权」）。

## 3. 设备接口层设计（核心）

> 本节直接借鉴 MHS 三条核心机制：① 每种设备一个 driver 映射到统一原语集；② 安全限制编译进接口层（作用于所有调用方）而非 agent prompt；③ 能力描述先行（agent 操作前先读参考文件）。

### 3.1 设计原则

1. **设备抽象（driver/适配层）**：每种设备一个 driver，把厂商私有接口（SDK/串口/CLI/文件掉落）映射为统一原语集。集成负担从「设备数 × agent 数」降为「每方各实现一次」——driver 写一次，任意 agent/脚本可复用。
2. **read/write 原语**：所有设备只暴露极简原语，消除「每种设备单独写翻译器」的集成爆炸。
3. **能力描述（reference file）**：设备自述「能读什么、能写什么、参数范围/单位、安全限制」，agent 操作前必须读取；能力描述是机器可读的注册文件，而非写在 prompt 里。
4. **自然语言能力标签**：把纸面手册/老师傅脑中的隐性知识（校准怪癖、环境依赖）以自然语言写入 driver，编译为参考文件的一部分。
5. **安全限制编译进接口层**：硬限/联锁在设备服务代码层强制执行，**作用于所有调用方（包括未来不可预见的 agent）**；prompt 级安全只作补充，不承担安全职责（MHS 教训：prompt 级安全随 harness 切换即失效）。
6. **「写逻辑时留 agent 接口」**：所有设备控制逻辑都经由统一接口层而非直写硬件——这是本架构对作者「写逻辑的时候要留 agent 接口」的工程化落地（见 §3.5）。

### 3.2 统一原语集

在 MHS 官方 read/write 基础上，采纳 Essa Mamdani 的扩展推断（read/write/describe/observe/stop），适配核电子学场景：

| 原语 | 语义 | 核电子学示例 |
|---|---|---|
| `describe(device)` | 返回参考文件（能力+限制） | HV 电源：可读 vset/vmon/imon/temp；可写 vset/ilim；限值… |
| `read(device, parameter)` | 读当前值（带时间戳+单位） | 读 vmon → `{value: 300.2, unit: "V", ts: ...}` |
| `write(device, parameter, value)` | 写参数（必经安全门） | 写 vset=310 → `accepted` 或 `rejected: 超出步进限制` |
| `subscribe(device, events)` | 订阅事件流（状态变化/告警/采集完成） | 订阅 `alarm` / `state_changed` / `run_done` |
| `stop(device)` | 安全停止语义（急停降级） | 高压断电、DAQ 停止采集 |

> 注：MHS 官方只确认 read/write + discovery；describe/observe/stop 为社区推断形态（调研报告 §3.2、§11 标注）。本设计按实际需求采用五原语，若 MHS 开源后规范不同则对齐（待作者裁定是否等 MHS 规范落地再定稿）。

### 3.3 参考文件（reference file）结构示例

每设备一份，driver 维护、自动编译、agent 操作前读取：

```yaml
device: hv_psu_01
type: 高压电源 (CAEN 类，示例)
capabilities:
  readable:  [vset, vmon, imon, ramp_speed, status, temperature]
  writable:
    vset:  {unit: V,  range: [0, 1000], step_max: 5, rate_limit: 50 V/min}
    ilim:  {unit: uA, range: [0, 500]}
  settable_while_running: [vset]
safety:
  hard_limits:                      # 确定性程序强制执行，任何调用方不可绕过
    vmon_max: 1100
    imon_trip: 550
    temp_max: 40
    temp_high_action: ramp_down_to_0
  interlocks:
    - if temp > 35 and ramp_active: pause_ramp
    - if imon > 300 sustained 5s:   ramp_down_50%
  human_approval_required:          # 审批门：超过此值需人工二次授权
    vset: 500
tags:                               # 自然语言隐性知识（老师傅经验/手册备注）
  - "夏季环境温度高时 vset 需低于 900V 避免过热"
  - "该台 vset 显示与实际输出偏差约 0.3%（校准 2026-03）"
  - "升压后需等待 30s 稳定再采集"
```

### 3.4 四类对外接口（「留 agent 接口」的具体形态）

| 接口面 | 形态 | 说明 |
|---|---|---|
| **状态读接口** | `GET /api/v1/devices` / `GET /api/v1/devices/{id}/state` | 全量状态快照 + 时间戳（Janelia「共享内存状态字典」同思路：异构仪器读同一份实时状态）；observer 权限即可用 |
| **参数写接口** | `POST /api/v1/devices/{id}/write`，body `{parameter, value, request_id, rationale}` | **必经安全门**；返回 `accepted` / `rejected + 原因`；所有写操作记审计日志（谁、何时、为何、结果） |
| **事件通知** | WS/MQTT 事件流：`state_changed` / `alarm` / `run_done` / `gate_rejected` | agent 长时值守靠事件驱动而非轮询（轮询浪费 token 且响应慢）；L1 Watchdog 依赖此接口 |
| **控制授权** | 令牌分级 observer / operator / approver；每设备可配；高险操作需 approver 二次签名 | 见 §5；多 agent 并发用「单操作员锁」（Gently 同款思路，调研报告 §9.2）防冲突 |

**MCP 暴露**：设备服务以 MCP server 形态把五原语暴露为 tools——任何支持 MCP 的 agent harness 都能接入（MHS 三种访问路径 MCP/CLI/code 的 MCP 一路）。同时提供 CLI（人机同界面：人类值班员与 agent 用同一套命令检查/操作设备）与 code 模式（把多步操作链成确定性脚本，长时任务不需要 agent 逐步推理——MHS 官方激光校准案例的收尾形态）。

### 3.5 「写逻辑时留 agent 接口」工程原则（落地指引）

对作者现有系统（DAMPE DAQ：Windows 上位机 CLI/GUI + FPGA 固件）与未来新写逻辑的通用要求：

1. **任何新设备控制逻辑一律走统一接口层**：设备服务是唯一触碰硬件的入口，禁止 agent/脚本绕过安全门直写硬件。
2. **三个「必须」**：
   - 必须有**状态读接口**——否则 agent 是瞎子，无法观察；
   - 必须过**安全门**——否则 agent 是脱缰的，无法兜底；
   - 必须有**事件通知**——否则 agent 只能轮询，值守不成立。
3. **现有系统的渐进适配**（DAMPE DAQ 可能无远程 API，待作者确认）：
   - **读侧**：包装 CLI 输出 / 监控掉落文件 / 串口回显 → 统一为 `read` 原语；
   - **写侧**：CLI 命令包装 + **参数白名单**（只允许安全门内的参数/取值到达命令层）；
   - 存量控制逻辑逐步迁入接口层，迁移期间安全门先以「读侧透明 + 写侧白名单」形态上线。
4. **技术栈建议（待作者裁定）**：设备接口服务用 **Python**（与 pyROOT/科学计算/仪器 SDK 生态一致，MHS 参考实现生态亦以 Python 为主）；与 Nebflow（Scala）通过 MCP 解耦，互不绑定。

## 4. 实验闭环

### 4.1 闭环状态机

```
                 ┌──────────────────────────────────────────┐
                 ▼                                          │
[协议就绪] → [初始化校验] → [观察] → [决策] → [执行] → [采集] → [分析] ──┘
             设备在位     读状态     继续/调整/停止  安全门校验  run 落盘  峰位/分辨率
             安全门自检   数据质量   (生成动作请求)  accepted    事件通知  质量评估
                 │
                 ├─ 状态异常 → [安全降级]（确定性程序执行：降压/暂停）
                 │                ↓
                 │           [告警] → [agent 诊断] → 恢复 / 上报人工
                 └─ 协议完成 → [汇总报告] → [人工接管/归档]
```

### 4.2 各环节职责与接口

| 环节 | 谁做 | 输入 → 输出 | 关键约束 |
|---|---|---|---|
| 观察 | L1 Watchdog + L2 状态读 | 设备状态、计数率、波形质量 → 状态画像 | 事件驱动，不轮询 |
| 决策 | L1 Protocol Agent + Analysis Agent | 状态画像 + 分析结果 → **动作请求**（`{参数, 目标值, 理由, 预期结果}`） | agent 只生成登记动作，不触达硬件 |
| 执行 | L2 安全门 + driver | 动作请求 → accepted/rejected | 硬限/联锁/审批门校验；高险动作挂起等人工 |
| 采集 | L3 采集服务 | run 配置 → 波形+元数据落盘 | run 记录含参数快照，保证数据-参数可回溯 |
| 分析 | L4 分析管线（Analysis Agent 调用） | run 数据 → 峰位/分辨率/效率/质量指标 | 结果带 provenance（数据文件+参数+分析版本） |
| 下一轮 | L1 Protocol Agent | 分析结果 → 下一参数点 / 继续 / 停止 | 协议边界与终止条件预先定义 |

### 4.3 借鉴 StarWhisper 的三处关键移植

1. **确定性程序保留最终执行权**：agent 生成的任何动作都只是「登记动作」，安全限位、联锁、人工接管始终由确定性程序（L2 安全门）掌握——与本架构 §5 完全同构。
2. **动作标签由专业约束给出，不由生成模型自行指定**：参数范围、步进上限、速率限制编译进参考文件/安全门，agent 的「自由发挥」被约束在专业约束之内。
3. **轨迹记录沉淀循环**：每条闭环迭代保存完整上下文（状态+动作+门控判定+结果+人工反馈），既沉淀实验 skill，又生成阶段 2 训练数据（见 §6.3、§7）。

### 4.4 Agent 角色划分

| Agent | 职责 | 说明 |
|---|---|---|
| Protocol Agent（实验长程） | 持有实验协议，编排各环节，决定「继续/调整/停止」 | 对应 StarWhisper 超级智能体中枢的调度职责 |
| Analysis Agent（分析） | 调 L4 分析管线，把数据转化为决策输入 | 峰位/分辨率/效率/质量评估 |
| Watchdog（监控/值班） | 长时值守，事件驱动，异常第一时间响应 | 对应作者「人盯参数」痛点的直接替代 |
| Safety Review（复核，可选） | 高险动作执行前的独立复核 | 与确定性安全门互补：门拦「硬越界」，复核拦「物理上不合理但未越界」 |

## 5. 安全模型

### 5.1 分层防护（自上而下，越往下越不可绕过）

| 层级 | 机制 | 负责方 | agent 可否绕过 |
|---|---|---|---|
| L0 物理层 | 硬件急停、机械限位、保险丝、UPS | 硬件 | 否 |
| L1 确定性保护层 | 硬限校验、联锁逻辑、速率/步进限制、自动降级（高压降压/暂停采集） | 设备服务代码（L2） | **否** |
| L2 审批门 | 高风险写操作需 approver 二次授权（如 vset > 500V） | 人工 | 否（人工） |
| L3 决策护栏 | 动作合理性预检（物理模型/经验规则）、重复动作抑制、异常频率检测 | 复核 agent / 规则引擎 | 可（软约束） |
| L4 Prompt 纪律 | 系统提示中的安全要求 | 各 agent | 可（仅补充） |

**核心原则（MHS 原话精神）**：「限制编译进 driver 的限制作用于所有调用方，包括你没想到的那个」——L1 是安全的主体，L3/L4 只是降低「物理上合理但不明智」动作的概率，不承担安全兜底。

### 5.2 分级授权

| 角色 | 权限 | 典型持有者 |
|---|---|---|
| observer | 只读：状态、数据、参考文件 | 分析 agent、Watchdog、值班员查看 |
| operator | 在安全包络内写参数（单步限制内） | Protocol Agent、值班员 |
| approver | 批准超出 operator 权限的高风险动作 | 实验负责人（人工） |

- 权限绑定到令牌/身份，**每设备可配**（如 HV 电源 operator 可写 ≤500V，超过需 approver）；
- 多 agent/多人并发写同一设备：**单操作员锁**（同一时刻只有一个 operator 持有写权限，防冲突）；
- 全部写操作与审批动作记审计日志（含动作理由 rationale），供事后回溯与轨迹记录复用。

### 5.3 异常路径

- **硬越界**：安全门拒绝，命令不到达硬件，触发 `gate_rejected` 事件（agent 可读到原因）；
- **联锁触发**（如温度超标）：确定性程序自动降级（降压/暂停），不经 agent 决策；
- **agent 失联/模型故障**：Watchdog 超时检测 → 维持当前安全状态（不主动调参）→ 告警人工；
- **人工接管**：任何时刻人工可接管（stop 原语 / 急停），接管后 agent 进入只读观察模式。

## 6. 数据管线

### 6.1 数据分类与存储形态

| 数据 | 内容 | 存储形态（建议） | 说明 |
|---|---|---|---|
| 波形数据 | 单事件：timestamp + channel + 波形 + 触发标签 | HDF5 或 ROOT，按 run 分文件 | 与作者领域 ROOT 生态兼容；HDF5 便于 Python 侧流式处理（待作者裁定） |
| run 元数据 | run 起止时间、参数快照（全设备状态）、配置、结果摘要 | SQLite 索引 + JSON 记录 | 保证「数据 ↔ 参数 ↔ 时间」可回溯 |
| 轨迹记录 | (状态, 动作, 门控判定, 结果, 人工反馈) | JSONL（§6.3） | 阶段 2 训练数据 + 实验 skill 沉淀 |
| 分析中间结果 | 能谱、拟合峰位/分辨率、质量指标 | 带 provenance 的 JSON/ROOT | 分析版本、输入文件、参数快照齐备 |

### 6.2 波形存储策略（量大、单事件小——核心权衡）

- 单事件约 1–2 KB（几百样本 × 12–14 bit），触发率 kHz–MHz 量级 → 全波形长期存储成本需权衡；
- **分层策略（建议）**：
  - 触发率低（<1 kHz，如 SiPM + 放射源台架）：**全波形存储**——阶段 2 训练数据完整保留；
  - 触发率高（束流/高计数率）：关键 run 全波形，长期 run 存摘要（幅值、时间、能量、波形特征）；
  - 无损压缩（zstd 等）+ 必要时下采样；
- **阈值判断标准待作者裁定**（取决于存储预算与阶段 2 训练需求：宁可前期多存，训练数据不能事后补）。

### 6.3 轨迹记录格式（阶段 2 训练数据的核心载体）

借鉴 StarWhisper「每条轨迹保存报告序列、天气输入、设备状态、动作及约束判定、后继状态、观测收益、失败码和数据标识」，核电子学对应物：

```json
{
  "trajectory_id": "run_20260901_003",
  "step": 12,
  "timestamp": "2026-09-01T14:23:05+08:00",
  "state": {
    "hv_vset": 300, "hv_vmon": 300.2, "temp": 22.5,
    "count_rate": 1234, "peak_pos": 456.7, "resolution": 8.2,
    "data_quality": "good"
  },
  "action": {
    "device": "hv_psu_01", "parameter": "vset", "value": 310,
    "rationale": "峰位偏低 5%，尝试升压补偿增益",
    "expected": {"peak_pos": "480±20"}
  },
  "gate": {"accepted": true, "checks": ["range", "step", "interlock"], "approver": null},
  "result": {
    "count_rate": 1300, "peak_pos": 470.1, "resolution": 7.9,
    "data_files": ["run_20260901_003.h5"], "analysis_version": "v1.2"
  },
  "human_feedback": null
}
```

每条轨迹 = 一次闭环迭代；全部轨迹构成「状态-动作-结果」序列，是阶段 2 训练与实验 skill 沉淀（哪些参数组合在什么状态下有效）的共同原料。

## 7. 阶段 2 前瞻：波形事件识别模型

### 7.1 与 StarWhisper 世界模型三件套的映射

| StarWhisper | Agentic Auto Experiment 对应物 | 说明 |
|---|---|---|
| 超级智能体中枢 | L1 编排 agent 簇 | 已在阶段 1 落地 |
| 目标世界模型（跨巡天时序：目标如何演化） | **物理事件世界模型**：不同粒子/能量在探测器+电子学中的波形形态（幅度/时间常数/堆积形态演化） | 波形是低维对象（单事件 ~K 样本），比天文大图（M 像素）维度低一个量级以上 |
| 天空模型（短时气象：环境如何变化） | **实验环境世界模型**：噪声底、基线漂移、温度→增益漂移、长期稳定性 | 对应 DAMPE 十年遥测可得的长期行为 |
| 设备数字孪生（机架/传感器/故障状态响应） | **探测器+电子学数字孪生**：Geant4（探测器响应）+ 电子学仿真（波形成形/噪声/ADC 量化） | 用于合成轨迹、故障复现、模拟验证，与真实运行分开（StarWhisper 同款纪律） |
| VLA 只生成登记动作，确定性程序最终执行 | L2 安全门 + 审批门 | 阶段 1 已落地，阶段 2 不变 |
| 轨迹记录 → skills + 训练数据 | §6.3 轨迹记录 → 波形分类训练集 | 阶段 1 自然积累 |
| 反事实轨迹（世界模型生成） | 数字孪生合成波形补充稀有/故障事件 | 解决「稀有事件真实数据不足」 |

### 7.2 训练数据如何从阶段 1 自然积累

| 标签来源 | 说明 | 自动化程度 |
|---|---|---|
| 触发类型/通道标签 | DAQ 自带 | 全自动 |
| 分析结果打标 | 峰位→能量标签、信号/本底分类 | 全自动（L4 管线） |
| 已知信号源 | 放射源特征峰、标准源刻度 | 全自动（已知期望） |
| 参数-波形关联 | 同一状态下的波形簇与动作历史关联 | 全自动（轨迹记录） |
| 人工标注稀有事件 | 阶段 2 模型辅助筛选 + 专家确认 | 半自动（后期） |

### 7.3 作者「训练比天文容易」判断的依据（本设计的认同与补充）

1. **维度低**：单事件波形 ~1K 样本 vs 天文图像 M 像素；模型输入小、训练快；
2. **数据量大且自然产生**：DAQ 本来就是流水线，触发率 kHz 以上，一个 run 就是几十万事件——无需专门采集；
3. **标注半自动**：物理上有先验（峰位、时间常数、触发条件），分析管线自动打标，人工只抽检；
4. **仿真成熟**：Geant4 + 电子学响应的模拟管线是核电子学标配，数字孪生合成数据可直接增强训练集。

补充提醒：波形虽单事件简单，但**事件间关联**（堆积、串扰、时间相关性）与**长时漂移**（增益随温度）是天文图没有的维度——阶段 2 模型除单事件分类外，需把「环境状态」作为上下文输入（对应世界模型的天空件）。

## 8. 落地路径与里程碑

### 8.1 切入场景建议：探测器测试台架参数扫描闭环

**建议从作者实验室台架（SiPM/CZT 测试）切入**，理由：

1. **设备在手**：不依赖大装置排期，随时可动；
2. **痛点最直接**：参数扫描机械重复 + 值守疲劳，agent 化收益立竿见影；
3. **安全包络清晰**：台架 HV/温度限已知，风险可控（不像束流实验有联锁复杂度）；
4. **数据自然积累**：每次扫描都产出波形+轨迹，直接喂阶段 2；
5. **衔接开题空白**：台架闭环验证后，向「无人值守束流标定 agent」（DAMPE 束流实验场景）推广——这是开题调研确认的学术空白区。

**备选/并行：模拟器先行**（数字孪生 M0）：在无硬件风险的数字孪生/仿真环境验证闭环与安全门逻辑，再切真设备——降低首轮风险（待作者裁定是否先跑模拟器）。

### 8.2 最小闭环验证（M1）：单参数自动扫描

**场景**：SiPM + 放射源，HV 从 100V 扫到 300V、步进 10V。
**闭环**：agent 下发 vset → 安全门校验（范围/步进/联锁）→ 等待稳定（30s）→ 采集 N 事件 → 分析（峰位/分辨率/计数率）→ 记录轨迹 → 下一档。
**输出**：分辨率-vs-HV 曲线（与人工扫描一致性对比）+ 轨迹数据集。
**验收（二值）**：
- 全程零人工干预（除启动与结束确认）；
- 安全门零越界（所有写请求或被接受或被拒绝且拒绝原因合理）；
- 自动扫描曲线与人工扫描结果一致（分辨率偏差 < 阈值，待作者给定）；
- 轨迹记录完整（每步 state/action/gate/result 齐全），可直接作为阶段 2 训练数据。

### 8.3 里程碑拆分

| 里程碑 | 周期（估） | 内容 | 验收要点 |
|---|---|---|---|
| M0 设备接口层骨架 | 1–2 周 | 2 个设备 driver（HV + DAQ）+ 安全门 + 能力注册表 + MCP 暴露；模拟器先行验证 | 模拟器上闭环可跑；安全门拦截逻辑单测通过 |
| M1 最小闭环 | 2–4 周 | 单参数自动扫描（§8.2）+ 轨迹记录 + 分析管线 | §8.2 四条验收全过 |
| M2 多参数值守 | 1–2 月 | 多参数联合扫描 + 数据质量监控 + 过夜值守（自动暂停/恢复）+ 告警链路 | 一次 ≥8h 无人值守 run 成功，异常事件全部正确响应 |
| M3 事件识别模型 v0 | 2–3 月 | 用 M1–M2 积累波形训练波形分类模型 | 分类准确率基准（待作者给定）；与仿真数据增强对比 |
| M4 复杂场景 | 长期 | 数字孪生增强、复杂实验协议、DAMPE 束流实验场景迁移 | 束流场景闭环；开题课题衔接 |

## 9. 风险清单

| # | 风险 | 等级 | 缓解措施 |
|---|---|---|---|
| 1 | **设备安全**：HV 打火、过流、探测器损坏 | 高 | L0–L1 确定性保护（硬限/联锁/自动降级）+ 物理急停 + 人工接管；安全门不经 agent 决策 |
| 2 | **LLM 幻觉调参**：提出物理上不合理参数 | 高 | 安全门硬拦（范围/步进/速率）+ 审批门（高险动作）+ 复核 agent（合理性预检）+ 重复动作抑制 |
| 3 | **数据可靠性**：数据丢失、参数-数据关联错误、时间戳漂移 | 中 | run 参数快照 + 校验和 + 审计日志 + 元数据双写；轨迹记录为数据-参数关联的唯一真相源 |
| 4 | **与现有 DAQ 集成兼容性**：DAMPE DAQ 为 Windows CLI/GUI + FPGA 固件，可能无远程 API | 中 | 读侧文件/CLI 适配 + 写侧白名单命令通道（§3.5）；M0 优先选有可编程接口的设备（HV 电源通常有） |
| 5 | **长时运行稳定性**：agent 进程/模型 24/7 值守 | 中 | Watchdog 超时检测、自动重连、状态落盘可恢复；agent 失联时维持安全状态 |
| 6 | **模型成本/延迟**：LLM 调用在值守中高频触发 | 低 | 事件驱动（非轮询）+ 决策低频 + 常规监控走确定性规则，LLM 只在异常/决策点触发 |
| 7 | **数据所有权/保密**：实验数据不出实验室 | 低 | 本地部署，数据不出实验室网络（待作者裁定）；LLM 用本地/内网模型或敏感数据脱敏 |

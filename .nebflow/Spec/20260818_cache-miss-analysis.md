## 6. 根因链

1. **provider prompt cache TTL 短（~30min）**：跨 provider 一致，非 Nebflow 可控
2. **agent 上下文大**（system prompt + 历史，单请求 60-100K input 常见）：缓存过期后全量重发成本高
3. **agent 长期不活跃 → 无保活**：team agent 闲置数小时后唤醒 = 首个请求全量计费
4. **flow 一次性 agent**（EntityArchitect/EntityTeamReviewer 等）命中率 65-75%：生命周期短、间隔大、每次新上下文
5. **107 网关命中率低**（46.9-80.4%）：litellm 代理层缓存策略弱于直连 provider

## 7. 缓解方向（按性价比排序）

### P0（零代码，立即可做）
1. **不活跃 agent 首唤醒走 LowCost**：识别 >30min 闲置的 agent，其唤醒 turn（间隔后第一请求）路由到 `107/deepseek-v4-flash-ascend`（免费 + 0.5s 快，即使全量也几乎零成本）。已在记忆/用户偏好中（"107/LowCost 免费多用"），落地为调度规则即可
2. **基线上下文精简**：agent system prompt 瘦身（系统提示词保持精简——用户既有偏好），降低每次全量输入基数（60K→30K 直接减半唤醒成本）
3. **控制并发唤醒**：批量唤醒（如明早 03:00 窗口）错峰/排队——与 P0 ConcurrencyGate 协同，避免同时 N 个 agent 全量请求打爆

### P1（代码）
4. **compaction 时机优化**：闲置 agent 压缩上下文（历史折叠）→ 唤醒时输入更小
5. **保活/预热机制**（探索）：活跃 agent 定期轻量请求刷新缓存（成本权衡——刷新本身消耗，仅对高频 agent 值得）

### P2（需产品决策）
6. **107 网关缓存调查**：deepseek-v4-pro 46.9% 命中率根因（网关配置 vs 请求特征），或换直连 provider

## 10. 方案对比

| 方案 | 机制 | 预期收益 | 成本 | 实施难度 | 风险 |
|------|------|----------|------|----------|------|
| **A. 不活跃首唤醒走 LowCost** | 间隔 >30min 的 agent 唤醒 turn 路由到 `107/deepseek-v4-flash-ascend`（免费+0.5s） | 唤醒全量 input 成本 → 0；250K 唤醒 × 免费 | 107 网关限流 20/60s（唤醒错峰可规避）；107 命中率本身低（46-80%）但**免费所以无所谓** | **低**（调度层规则，无架构改动） | 107 模型能力差异（vision=false、推理模型延迟）——唤醒 turn 通常简单（问候/上下文加载），低风险 |
| **B. 基线上下文精简** | system prompt 瘦身（记忆渐进披露收紧/工具描述精简/团队规则压缩） | 大上下文 system 65K→50K（-23%）；**每次全量请求（含唤醒）直接减基数** | 需 prompt-engineer 逐 agent 审查；精简过度丢信息 | **中**（跨 agent 系统性改动，需回归） | 能力退化风险（信息不足） |
| **C. 批量唤醒错峰** | 定时批量任务（03:00 窗口/明早汇总）唤醒 N 个 agent 时排队/串行，避免同时全量请求 | 避免 N×250K 同时突发；与 P0 ConcurrencyGate 协同 | 批量任务完成时间延长 | **低**（调度规则） | 任务延迟 |
| **D. 闲置压缩** | 闲置 agent 触发上下文压缩（历史折叠）→ 唤醒时输入更小 | 唤醒 input 250K→50-80K（历史折叠后） | 压缩本身消耗一次 LLM 调用；压缩后上下文信息损 | **中-高**（触发机制+压缩策略） | 压缩质量；与现有生命周期压缩机制重叠 |
| **E. 保活预热** | 高频 agent 定期轻量请求刷新 provider 缓存 | 维持 90%+ 命中 | 保活请求本身消耗（~1K/次 × 频次）；仅对高频 agent 值 | **中** | 保活频率失控=新消耗源 |

## 11. 推荐组合与实施路径

**推荐：A + C 先行（零代码，调度层规则）→ B 次之（prompt-engineer 系统性优化）→ D 视需（压缩机制已有基础）→ E 不推荐（成本权衡不佳）**

| 阶段 | 组合 | 预期效果 | 实施难度 | 负责 |
|------|------|----------|----------|------|
| **P0（零代码）** | A 首唤醒 LowCost + C 批量唤醒错峰 | 唤醒成本 → 0；批量突发消除；**与 P0 ConcurrencyGate 直接协同**（107 RPM=15 的排队天然错峰） | 低（调度规则/工具描述） | Nebula/Manager 调度规则 |

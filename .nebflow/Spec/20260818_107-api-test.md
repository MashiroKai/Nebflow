# 107 API 稳定性测试报告（llm.example.com）

- 日期：2026-08-18
- 测试人：Backend（nebflow-project）
- 上下文：P0 并发管理任务 ② —— 为 ConcurrencyGate 提供 107 网关的 RPM/并发参考值；107 是 USTC 免费网关（LowCost preset 首选）
- 状态：完成即冻结（阶段文档）

## 1. 结论摘要

| 项 | 结论 |
|----|------|
| 可用性 | ✅ 可达，HTTP 200，直连 connect ~42ms（本地校园网） |
| 协议 | Anthropic 协议（`/v1/messages`），Nebflow 配置 `protocol: anthropic` 正确 |
| 限流 | ⚠️ **20 requests / 60s 滑动窗口（litellm 后端，按 api_key）**，突发超限返回 429 |
| 延迟 | 波动极大：0.7s ~ 60.5s（推理模型 glm-5.2-107/k3 最慢），**p95 并发 8 档达 44.8s** |
| 推理模型 | glm-5.2-107 / k3 是 reasoning 模型（`reasoning_content`/`thinking` 块），deepseek 系列不推理 |
| Nebflow 兼容 | ✅ AnthropicAdapter 全兼容（thinking_delta→ThinkingDelta、`[DONE]` 显式忽略、message_start/delta usage 双源） |
| 风险 | 高负载下单请求 60s+ 逼近 LlmFirstTokenTimeoutSec=90s；429 在 Nebflow 会触发 fallback 链重试 |

## 3. 协议探测（Anthropic，与 Nebflow AnthropicAdapter 请求一致）

端点 `POST https://llm.example.com/v1/messages`，头 `x-api-key` + `anthropic-version: 2023-06-01`。

| 模型 | 模式 | content | thinking | 延迟 | 备注 |
|------|------|---------|----------|------|------|
| glm-5.2-107 | 非流式 | OK | 186 chars | 3.3s | 推理模型，thinking 块先行 |
| glm-5.2-107 | 流式 | OK | 29 thinking_delta | 3.2s | 标准 Anthropic SSE |
| k3 | 非流式 | — | — | — | 见 §4 OpenAI 探测 |
| deepseek-v4-pro | 非流式 | OK | 0 | ~7-29s | 不推理但偶发慢 |
| deepseek-v4-flash-ascend | 非流式 | OK | 0 | 0.5-0.8s | **最快**，LowCost 首选合理 |

### 3.1 流式事件序列（glm-5.2-107，max_tokens=64）

```
message_start (usage: input/output)
content_block_start (type=thinking, signature="")
thinking_delta × 29（推理过程逐字流出）
signature_delta ("")
content_block_stop
content_block_start (type=text)
text_delta ('OK')
content_block_stop
message_delta (stop=end_turn, usage: input=14, output=59)
message_stop
data: [DONE]   ← 网关附加的 OpenAI 风格结束标记
```

**关键**：网关在 Anthropic 流末尾附加 `data: [DONE]`——非合法 JSON。Nebflow `AnthropicAdapter.processAnthropicEvent` 第 349 行 `if data == "[DONE]" then IO.pure(Nil)` 已显式处理（issue #18 加固），兼容 ✅。thinking 块签名空（`signature=""`），Nebflow 会过滤空签名（content_block_start 处 `.filter(_.nonEmpty)`）✅。

### 3.2 Nebflow 适配器兼容性清单

- `message_start`：从 `message.usage` 抓 input/cache_read/cache_creation ✅
- `thinking_delta` → `StreamChunk.ThinkingDelta` ✅
- `signature_delta` → `ThinkingSignature`（空过滤）✅
- `text_delta` → `TextDelta` ✅
- `message_delta`：`input_tokens` 回退逻辑（delta 非零优先，否则用 message_start）✅
- `[DONE]`：显式忽略 ✅
- 历史重放：107 的 requireThinkingPassback=false（默认，仅 deepseek 特判 true）——glm-5.2-107 的 thinking 块无签名会在重放时丢弃。**风险点**：若 107 网关对历史消息强制要求 thinking passback，会出现与 deepseek 相同的历史重放拒绝。当前未实测（需要真实多轮对话验证）。

## 4. OpenAI 协议对照探测（网关双协议，Nebflow 不用）

`POST /v1/chat/completions`（OpenAI 协议）——仅对照参考，Nebflow 走 Anthropic：

| 模型 | max_tokens | content | 延迟 | 备注 |
|------|-----------|---------|------|------|
| glm-5.2-107 | 64 | **None** | 2.7s | reasoning 吃光预算，finish=length |
| glm-5.2-107 | 256 | OK | **41.6s** | 极慢 |
| k3 | 64 | OK | 33.5s | 慢 |
| k3 | 256 | OK | 9.3s | |
| deepseek-v4-flash-ascend | 64 | OK | 0.47s | 快 |
| deepseek-v4-flash-ascend | 256 | OK | 0.78s | 快 |
| deepseek-v4-pro | 64 | OK | 29.3s | 慢 |
| deepseek-v4-pro | 256 | OK | 6.8s | |

**关键**：
1. **OpenAI 协议下 glm-5.2-107 非流式 41.6s vs Anthropic 协议 3.3s**——协议路由差异巨大（网关对 Anthropic 端点可能走不同上游/配置）。Nebflow 配置 anthropic 协议是正确选择。
2. glm-5.2-107 在 max_tokens=64 时 content=null（reasoning 吃光）——Nebflow `hasReasoningContent` 防误判空响应（OpenAiAdapter:164），但返回的是**空 content 的 AdapterResponse**，agent 会收到空回复且不触发 fallback。max_tokens 必须给足（≥256 才稳定出 content）。
3. **延迟波动巨大**（同模型同参数 33.5s vs 9.3s）——网关共享资源，负载敏感。

## 5. 阶梯加压测试（Anthropic 协议，glm-5.2-107，12 rounds/档，max_tokens=512）

脚本：`/tmp/107-loadtest.py`（python 线程池，urllib 阻塞，90s 超时）

| 并发 | 成功 | 429 | p50 | p95 | max | 吞吐 | wall |
|------|------|-----|-----|-----|-----|------|------|
| 1 | 12/12 | 0 | 3.8s | 9.1s | 9.1s | 14 rpm | 50.9s |
| 2 | 12/12 | 0 | 2.8s | 8.0s | 8.0s | 35 rpm | 20.8s |
| 4 | **9/12** | **3** | 10.7s | 24.3s | 24.3s | 13 rpm | 41.9s |
| 8 | **9/12** | **3** | 4.1s | **44.8s** | 44.8s | 11 rpm | 48.5s |

### 5.1 关键结论

1. **429 限流出现于并发 ≥4 档**：错误体 `litellm.RateLimitError: Rate limit exceeded for api_key: ... Limit type: requests. Current limit: 20, Remaining: 0`。结合时序（各档 2s 冷却、累计 48 请求/162s），判定为 **20 requests / 60s 滑动窗口**（litellm 默认）。
2. **并发 4 档延迟暴涨**：p50 2.8s → 10.7s（3.8×），p95 24.3s——网关开始排队/降速。
3. **并发 8 档 p95 44.8s**：逼近 LlmFirstTokenTimeoutSec=90s 的一半；若网关负载更高可能超时。
4. **有效吞吐上限 ~35 rpm**（并发 2 档），再往上并发不增吞吐反而降（429 + 排队）。
5. **突发并发不增加吞吐**：并发 4/8 的有效吞吐 11-13 rpm 反而低于并发 2 的 35 rpm。

### 5.2 对 ConcurrencyGate 的建议参考值

| 参数 | 建议值 | 依据 |
|------|--------|------|
| 107 最大并发 | **2**（保守）~ 4 | 并发 2 无 429 且吞吐最高；并发 4 开始 429 |
| 107 RPM 参考 | **≤15**（保守，留 25% 余量）| 20/60s 窗口；Nebflow 自身 retry/fallback 会放大 |
| 429 处理 | 退避 ≥60s 后重试或直接 fallback | litellm 窗口 60s |

## 6. 限流窗口专项探测

脚本：`/tmp/107-ratelimit.py`（单线程连续请求，记录完整 429 body）

| 场景 | 结果 |
|------|------|
| glm-5.2-107 慢速串行（0.5s sleep，实际 ~5-6 rpm） | **25/25 OK 无 429** |
| deepseek-v4-flash-ascend 0 间隔串行（实际 ~10 rpm，含 27-48s 慢请求） | **25/25 OK 无 429** |
| 压测并发 4/8 档（突发，窗口内累计 >20） | **429 × 3/档** |

**判定：20 requests / 60s 滑动窗口**（litellm 后端按 api_key）。慢速低速率不触发，突发累计超窗口触发。

- 429 完整 body（从压测捕获，截断于 200 字符）：
  ```
  {"error":{"message":"litellm.RateLimitError: Rate limit exceeded for api_key: <key>.
  Limit type: requests. Current limit: 20, Remaining: 0. L..."}
  ```
- 注：429 body 的 retry_after/window 秒数字段在本次探测中被脚本截断（HTTPError.read()[:200]），未拿到精确值。如需精确窗口秒数，需单独发一次完整 429 抓全 body（可在压测 429 出现时用 curl 补抓）。
- 慢请求伴随现象：fast 模型 0 间隔串行时第 15-18 个请求出现连续 27-48s 慢响应——**网关共享资源，连续打负载会整体变慢（任何模型）**。

## 7. 风险与建议

### 7.1 推理模型慢延迟（P1 关注）

- glm-5.2-107（当前 default）单请求 3.3s~60.5s，p95 并发下 24-45s。
- **Nebflow 首 token 超时 90s**（LlmFirstTokenTimeoutSec）——60s 实测已过半，高负载时可能超时 → 触发 fallback 链重试（放大 token 消耗，2026-08-18 token 事故同族）。
- **建议**：default 保持 glm-5.2-107 但关注超时；低延迟需求（agent 子任务、批量）显式用 `107/deepseek-v4-flash-ascend`（低负载 0.5s；高负载也会慢至 48s）。

### 7.2 空 content 陷阱（P1）

- glm-5.2-107 在 max_tokens ≤64 时 content=null（reasoning 吃光），Nebflow 拿到空回复但不报错（hasReasoningContent 防误判）。**agent 会静默收到空回复**。
- 建议：107 的 glm/k3 模型 maxTokens 配置保持 ≥256（当前 64000 无此风险）；如需严格校验可考虑 adapter 对 reasoning-only 响应告警。

### 7.3 限流与并发（P0 直接相关）

- 20 requests/60s 窗口 = **RPM 参考值 20**（建议 ConcurrencyGate 用 15 保守值）。
- 并发 >2 不增吞吐反降（429 + 排队延迟），107 网关不是靠并发压吞吐的类型。
- **多 agent 并发唤醒 107 时必须排队**——这正是 P0 并发管理解决的问题；107 的 ConcurrencyGate 配置建议 maxConcurrent=2、RPM=15、429 退避 60s。

### 7.4 thinking 块历史重放（P2，未验证）

- 107 requireThinkingPassback=false，glm-5.2-107 的 thinking 块无签名，多轮对话历史重放时会被丢弃。
- 若网关强制要求 thinking passback（类 deepseek），会 400 → provider DOWN。**需真实多轮对话验证**（当前测试均为单轮）。

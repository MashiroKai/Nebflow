## Scope and classification

Behavior changes, specified in `specs/chat-composer/spec.md`: recall of attachments from the input history (FCC-REQ-001), a retry for one failed media item (FCC-REQ-002), opening AskUser reply attachments (FCC-REQ-003), legible Ask history (FCC-REQ-004) and the desktop conversation host (FCC-REQ-007). Behavior that already existed and is now pinned by a real test: the input-method Enter contract (FCC-REQ-005) and the single return entry (FCC-REQ-006). Nothing here changes a gateway message, a tool, a prompt or a provider setting.

## Input history keeps attachments

`state.inputHistory` stays the plain list of texts that earlier builds and other readers understand. `js/input/historyStore.js` records every sent message once, at the point where the frame is written (direct send, queued drain, immediate send and offline flush all go through `recordSentInput`), and keeps a ledger with one slot per text:

- Slot metadata (type, name, mime type, hash, size, reference fields) is stored in localStorage under its own key. The payload (base64) is written to the queue vault's IndexedDB under `hist:<entryId>:<index>` keys, which the queue's own orphan sweep skips, and is also kept in memory for the page's lifetime so that a recall works immediately.
- The ledger is matched to the text list from the tail by a text signature (`js/input/historyLedger.js`). A text appended by a build that knows nothing about the ledger breaks the match there: older entries come back as text only. Entries are never paired with the wrong attachments, and no cross-store atomicity is claimed.
- Caps: the 200-entry text bound is unchanged; the newest 30 entries keep attachments and at most 64M base64 characters in total, in-memory copies at most 16M. Entries leaving a cap release their stored payloads, and a once-per-page sweep (it reads the keys the ledger refers to after the store's key listing came back, so a message recorded meanwhile is not swept) removes payloads no slot refers to. A reference whose text is longer than 16K characters keeps that text with the payloads in IndexedDB, not in the ledger: the ledger lives in localStorage, a small quota shared with the rest of the page.
- Recall (ArrowUp/ArrowDown at the ends of the input) restores the text at once and the attachments when their payload is read; a per-view ticket makes a slow read land only if the view still points at that entry. Attachments added by hand are never touched, only what the previous recall added is replaced or removed. An attachment whose payload is gone is not restored; one toast reports how many, and nothing hollow can be sent. An attachment that never carried a payload (a large file resolved by hash on the server) is restored exactly as it was sent.
- Limits stated honestly: payloads exist only where the browser still keeps them (cleared site data or an evicted quota loses them and is reported at recall time); two tabs writing history at once can break the tail match for older entries (they degrade to text only).

## One failed media item

The shared failure face in `popArtifacts.js` (`markMediaFailed`, the card note) can carry a retry control. The control is a sibling of the note, so the note's text is unchanged for everything that reads it. A retry clears the failed state of that element only (`clearMediaFailure`) and runs the load again; `hydrateMedia` tracks the listeners of its last run per element, so repeated retries never stack handlers. Surfaces:

- main conversation and Pop cards: the face's `hydrateMedia` is re-run for the item;
- stacked layers in the contact windows: the layer's byte leg (`attachMediaBytes`) is re-run for that item, siblings and the message are untouched; a second failure is retryable again (the single flat card kept its existing retry). A layer has two faces (collapsed and expanded) that fail and recover together: a retry from either one clears the failed state of both. The collapsed face captures the pointer for its swipe, which sends the click of a control inside it to the face itself, so a press that starts on a button inside the face does not start the swipe;
- input thumbnails: a failed thumbnail stays in the strip as a dashed item whose whole box is the retry control; the remove control stays reachable.

## Reply attachments open

The chip of an AskUser reply attachment is a group whose one preview control is the button around its thumbnail; a click anywhere on the chip (outside its own remove and retry controls) opens the preview too. The chip itself is not a tab stop: the first control in its tab order is the preview button, then the remove button. The remove and retry controls are therefore not nested inside another interactive element, which assistive technology would otherwise lose (the children of a button are presentational). Click, Enter or Space open the preview through the shared routes: the system viewer on the mobile layer (`mediaOpenRoute.openMediaDirect`), a Canvas tab through `attachmentPreview.previewBlob` on desktop. The bytes are the File the user picked, which is in memory whether or not the upload finished. A type nothing can render is reported. The remove and retry controls are separate buttons and are excluded. Nothing about the upload, the nine-item limit or the secret and choice-question restrictions changes.

## Ask history legibility

The per-bubble opacity writer (`syncAskFade`) is removed. The earlier behavior dimmed a bubble to 55% as soon as its top reached the column's top band, which washed out the visible part of the text. A bubble crossing the top edge is now clipped by the column; `--ask-fade-h` remains as plain padding. Three older oracles that pinned the dimming (`ask-glass-drag` D2, `ask-sheet-fade-height` A0b/A1/A3/D3, `canvas-ask-dock` F3) were rewritten to the new contract; their other assertions (no column mask, real blur, geometry) are unchanged.

## Input-method Enter

The composition predicate has one home (`imeGuard.js`) and is used by the main composer, the Ask dock and the friend, group and device composers. The new evidence drives it with the browser's own pipeline: Chromium's `Input.imeSetComposition` and `Input.insertText` produce real composition events, the confirming Enter arrives while the composition is active (Chromium order), and a keyCode-229 Enter after compositionend reproduces the WebKit order. Neither sends; the next independent Enter sends once. This exists on Chromium only; a real input method on WebKit/Safari, mobile soft keyboards and other OS input methods remain manual checks.

## Return entries

`scrollPill.js` already allows one visible pill per host, with the search-return pill as a separate meaning. The new evidence covers the main conversation (away, new messages, return) and the pair Agent/conversation: the Agent's pill is hidden with its view while a conversation is shown and is back, still correct, on return.

## Desktop conversation host

`js/messages/mainHost.js` mounts the unchanged conversation window (`renderChatModal`) into `#main` instead of a dialog on the desktop layer; the mobile layer keeps its dialog shell, which its page controller adopts.

- The Agent view (`#chat`, `#input-area`, `#top-overlays`) stays in the DOM, hidden by `visibility` and `inert`, so its draft, attachments and scroll position are exactly as left. Its return pill and top band are hidden with it.
- The conversation's identity (avatar, name, sub line, group settings, device description, selection count) moves into `#header`'s centre block, which also keeps the Agent controls that do not apply (session safety mode, voice, background indicators) out of the header. The sidebar toggle, search, scheduled tasks and canvas controls stay. The window's own `×` is hidden: the way back is the flipped avatar, plus Escape. The header's adaptive layout is asked to measure again when the centre changes.
- The activity-bar avatar flips (a short card flip, immediate with reduced motion) to the Agent face (the Agent's own avatar or the brand mark); while that face is shown the avatar's click returns to the Agent instead of opening the account entry, and the account face is the avatar's business again afterwards. The flipped avatar's title and label say so.
- The window's scroll area clears the floating header with a measured offset (`--fm-head-h`), and its input bar uses the main input bar's edge slot and bottom.
- Per-conversation state: draft text and reading position (with an at-bottom flag) are kept per conversation key when a conversation is replaced or closed and restored by its next opening. The key is the conversation id, or the friend's id while the conversation does not exist yet, so two such conversations never share one. Drafts of different conversations never mix, and the Agent's state is untouched because its DOM is. Opening the conversation that is already shown does nothing.
- Answers that outlive their window: a sync or a send answers after the user has moved on. The window shown by then belongs to another conversation, and the module-level message list is that one's. Three rules keep the two apart: (1) a conversation's local copy is only ever written while that conversation is the one shown (`persistConversation` refuses otherwise), so an answer for a conversation that was left stores nothing and the keyset watermark of its copy stays true; (2) what a send's answer changes outside its own window (the open conversation id, closing the window) happens only if that window is still the one shown; (3) an unsent text that comes back goes into the input of the window that sent it while that window is shown, and otherwise into the draft kept for its conversation: a final refusal always returns it, and any other failure returns it once the window that held the failed bubble (and its retry key) is gone. The failure is reported through the page toast when the window is no longer shown. The copy of a conversation that was left with a send in flight simply misses that message until the next sync, which fetches it from the server.
- Header search while a conversation is shown opens the existing conversation-scoped search of that conversation (`chatSearch.openSearchModal(scope)`), the Agent history search otherwise.
- The group settings drawer opens at the top of the window, below the header, because the header is no longer a sibling of the window.
- The Agent comes back when it is asked for: selecting an Agent session (the current one included), or the gateway creating or activating one (a session list with another active id), emits `AGENT_VIEW_REQUESTED` (`events.js`) and the conversation shown in the main area closes. The sidebar has no session list in this build, so the function every selecting path calls (`switchToSession`) and the session list frame are the paths; an unrelated refresh of the session list does not emit it.
- Escape: the conversation's document-level Escape handler acts only when the key is aimed at the conversation (focus in its window or header) or at the page body, and no other handler consumed it first (`defaultPrevented`: the page's global handler closes dropdowns and overlays that way). Settings, search, viewers and dialogs close with their own Escape handling, and their focus is inside them, so the same key no longer leaves the conversation as well.
- Paste: the Agent composer's document-level paste handler skips the event while that composer is inert (hidden under a conversation), so an image pasted into a conversation input is not attached to the Agent invisibly. Conversation inputs have no image paste of their own; that stays as it was.
- The avatar flip: the account title and label are read when the flip is requested (not half way through it), the periodic status refresh keeps the account title current without writing it while the Agent face is shown, the flip class is removed when the animation has ended (a timer is only the way out if no animation runs), and asking for the face that is already shown cancels a flip that was on its way elsewhere without touching the tooltip.

Known limits, kept visible: at narrow widths the header's adaptive layout may hide the search icon when a long device name or sub line crowds the centre; the Agent's pending questions and background indicators are not shown in the header while a conversation is shown (they are back on return); the visual design of the host is a large change that needs the user's real-screen confirmation (FCC-SCN-011).
